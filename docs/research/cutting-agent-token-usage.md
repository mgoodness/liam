# Cutting Coding-Agent Token Usage via Tool-Output Format

Research triggered by the user asking for investigation of a TheNewStack article on reducing coding-agent token usage, to check its claims against primary sources and map any real findings onto liam's design.

Source: [thenewstack.io/cut-coding-agent-tokens](https://thenewstack.io/cut-coding-agent-tokens/) — "Cut coding agent token use with better tool output," by Prasenjit A. Sarkar, Aug 31 2026. **Note up front**: this is a sponsored post — the byline states "Sonar sponsored this post. Insight Partners is an investor in Sonar and TNS," and the author is Sonar's own "product and solutions marketing manager." Its scope is narrower than the task brief assumed: it is entirely about *tool-result serialization format* (JSON vs. a format called TOON), not about compaction, sub-agent context isolation, prompt caching, or RAG-style retrieval. Those other techniques are real and well-documented elsewhere, but this specific article doesn't discuss them — it was fetched directly via `curl` (the article's actual body is server-rendered but WebFetch's renderer only surfaced the site chrome/newsletter modal, so raw HTML was pulled and stripped by hand) and the citations below are cross-checked against the primary sources it points to, not just the secondary write-up.

## What the article actually argues

Its single claim: verbose JSON returned by developer tools (issue lists, findings, logs) makes an LLM pay repeatedly for field-name/punctuation scaffolding on every record in a uniform array, and that's a token cost lever independent of model choice or prompt length. Its proposed fix is [TOON (Token-Oriented Object Notation)](https://github.com/toon-format/toon) — a format that declares a uniform array's field names once in a header, then emits one row per record (YAML-style indentation for nested data, CSV-style rows for uniform tabular data). It frames TOON as a drop-in *output-format* choice at the tool boundary, not a change to the agent, the model, or the protocol.

Two direct-quote claims in the article are attributed to unnamed sources ("Token costs are shaped not only by what coding agents read..." / "A regular structure gives a model..." / "A cheaper context that causes a weaker decision is not a cost improvement.") — no attribution is given for any of the three; they read as the author's own framing presented as pull-quotes, not citations to a third party. Treat these as opinion, not verified fact.

## TOON verified against its own primary source

[toon-format/toon on GitHub](https://github.com/toon-format/toon) is real, actively maintained, and does publish benchmarks — this checks out independently of the article:

- Encoding: four forms (inline primitive arrays, tabular form for uniform-object arrays, keyed-tabular, and a list fallback for non-uniform data) layered over YAML-style indentation.
- Its README benchmark: 244 data-retrieval questions across 4 models (Claude Haiku, Gemini 3.6 Flash, GPT-5.4-nano, Grok-4.5), 6 formats compared (TOON, JSON, JSON-compact, XML, YAML, CSV), tokenized with GPT-5's `o200k_base`. Headline numbers: TOON 72.2% ±2.8 accuracy at 2,474 tokens (29.2 acc%/1K tok) vs. JSON-compact 69.0% at 2,892 tokens (23.8 acc%/1K tok) — TOON wins on both axes in that run, but the gap is model-dependent (e.g. Grok-4.5 was 97.1% TOON vs. 96.3% JSON — barely distinguishable; Claude Haiku 65.6% vs. 63.5%). CSV is explicitly excluded from the overall ranking because it only supports 109/244 questions (flat tabular data only) — TOON's edge over CSV specifically on flat data was small (63.1% vs. 62.2%, at ~6% more tokens).
- The README itself flags that absolute token counts are tokenizer-specific and only the *relative* format differences are claimed to hold directionally — consistent with the article's own caveat to measure a team's actual payload rather than trust a universal percentage.

**Independent counter-evidence found**: a [DEV Community critical-analysis post](https://dev.to/ikaganacar/toon-benchmarks-a-critical-analysis-of-different-results-5h66) reran comparisons and reported TOON placing 9th of 12 formats (47.5% accuracy) on tabular data and last (43.1%) on nested data in its own test, against the official README's own reported 68.7%-vs-65.7% framing for one of its benchmark passes. Its explanation: TOON's official benchmark suite is "heavily weighted toward scenarios where TOON was designed to win," and results are highly model- and structure-dependent — a model that does well with TOON on one dataset shape (e.g. GPT-5-nano at 96.1% in the official run) can score far worse on a different shape (43.1% in the independent nested-data run). This is a real, substantive disagreement between the format's own maintainers and an independent tester, not a settled result — the article cites only the favorable side.

The article's own first-party number ("TOON used 49% fewer characters than pretty-printed JSON and 33% fewer than minified JSON") is explicitly the author's own one-off 25-issue comparison ("I saw this myself when generating a representative 25-issue comparison") — n=1 sample, unpublished methodology, not independently reproducible from what's given. It roughly matches [Sonar's own blog post](https://www.sonarsource.com/blog/tokenomics-of-quality/) framing ("cuts the size... by roughly a third to a half versus JSON"), which is unsurprising since both come from the same vendor.

**Verified as a real, shipped feature** (not just marketing copy): the [SonarQube CLI's output-formats docs](https://docs.sonarsource.com/sonarqube-cli/using-sonarqube-cli/output-formats) confirm `sonar list issues --format toon` is a real, documented CLI flag alongside `json`/`table`/`csv`, explicitly recommended "when piping data into Claude Code, Copilot, Codex, Cursor, or Antigravity."

## What this implies for liam

**The directly relevant finding**: liam's built-in tools already default to the practice this article is arguing for, independent of and prior to this article. Per `internal/tool/tool.go`, `Result.Content` is a plain `string`, and every existing built-in tool (`bash.go`, `read.go`, `write.go`, `edit.go`, `skill.go`) returns plain text — no tool marshals JSON into `Content` (`json.Marshal`/`MarshalIndent` calls in the codebase are confined to `internal/hook/hook.go`'s hook-payload stdin, `internal/skill/trust.go`'s trust-manifest file, and `internal/config/load.go`'s config merge — none of these are model-facing tool output). Issue #41's Testing Decisions section independently names this a deliberate convention: "golden-file tests... for the plain-text tool output conventions (`find`, `grep`, `web_search`, `web_fetch`)." So the article's core thesis — avoid repeated JSON scaffolding in tool output fed to a model — is already liam's status quo for every built-in tool, for unrelated reasons (plain-text output is simpler to golden-file test and read in the TUI). This article doesn't change that design; it's independent validation of a decision liam already made.

**Where it could matter, and doesn't currently**: today none of liam's tools return large *uniform tabular* data (issue lists, structured findings) — `bash` returns raw combined stdout/stderr, `read` returns a raw file. TOON-style tabular compaction is specifically for arrays of same-shaped records, which liam doesn't yet produce anywhere. It would become directly relevant if/when liam grows a tool that returns many same-shaped records (e.g., a hypothetical lint/test-results tool, or an MCP server's tool results that happen to be uniform JSON arrays) — at that point this article (and TOON specifically) is one candidate lever, though the counter-evidence above means it shouldn't be taken as settled that TOON wins across models and data shapes.

**MCP connection, currently hypothetical**: issue #41's MCP section (`### MCP`) already anticipates a context-budget problem from connected servers, but at the *tool-count* level — an optional `tools` allow-list "to protect the context budget," addressing how many tool schemas get advertised, not the shape of what a tool call returns. This article's concern (output-format bloat per call) is a different, complementary lever that issue #41 doesn't currently address at all. As of this research, `internal/config/config.go`'s `MCPServersConfig` is literally an empty stub struct with the comment "populated by a later ticket" — no MCP client exists yet in the codebase, so there's no current code path where an MCP server's tool-result format (JSON-heavy or otherwise) reaches liam's agent loop to evaluate.

**Compaction/context-tracker connection**: `internal/session/session.go`'s `Session` struct already tracks `LastContextTokens` and `CostUSD`, but per its own doc comment this is "the minimal seat" for ticket #52's fuller mechanism — `internal/agent/agent.go`'s `Loop.Run` has no compaction logic at all yet (it's a pure dispatch loop: stream, collect tool calls, dispatch, repeat). Issue #41's `### Compaction` section specs a sliding-window-plus-summarization-call design (`/compact`, auto-triggered at ~85% usage) that explicitly treats "tool outputs and conversational turns... uniform[ly] in v1," naming "targeted pruning of large old tool outputs specifically" as an explicit v2+ deferral (also listed in Out of Scope). Neither `bash.go` nor `read.go` (nor any other current tool) truncates large output today — a large `bash` command's full combined stdout/stderr, or a large file's full contents, goes straight into the conversation with no cap. This article's format-level lever (smaller output per call) and issue #41's already-deferred truncation lever (capping/pruning output post-hoc) are two different mitigations for the same underlying problem — this article doesn't resolve which liam should prioritize, since it never discusses truncation or pruning at all.

**Skills connection**: no meaningful overlap — the article's subject (structured tool-result serialization) is unrelated to liam's on-demand skill-loading design (`internal/skill/skill.go`, `internal/tool/skill.go`'s `ActivateSkill`), which is about *when* content enters context, not *how densely* it's encoded once it does.

## Open question(s) this doesn't answer

- Whether liam should ever adopt a non-JSON, non-plain-text structured output convention (TOON or otherwise) for a future tool that returns uniform tabular data is not something this article resolves — the independent counter-benchmark found above means "TOON is strictly better" isn't a settled claim even within its own stated use case, and liam has no such tool today to apply it to.
- Whether liam's existing plain-text tool-output convention should get an explicit truncation/size-cap policy (distinct from issue #41's already-deferred "targeted pruning during compaction") is a real open design gap this research surfaced — `bash` and `read` both currently return unbounded output — but it's a liam-specific gap this article didn't prompt or address; it predates this research.
- Whether a future MCP allow-list (issue #41's `tools` config) should also account for a connected server's *output* verbosity, not just its tool count, is a genuinely open extension of issue #41's stated concern that this article's central thesis suggests but issue #41 itself doesn't currently scope.
