## Architecture layering: `pi-ai` → `agent` → `coding-agent`

pi.dev is built in three layers, each a separate npm package in the monorepo:

1. **`packages/ai`** (`@earendil-works/pi-ai`) — the provider/model abstraction: `Tool`, `Context`, `Message`, `AssistantMessageEvent` stream protocol, per-provider adapters.
2. **`packages/agent`** (consumed as `@mariozechner/agent` per import paths in its own tests, published separately from the CLI) — a **reusable, UI-agnostic agent-loop + harness library**: `agentLoop`/`agentLoopContinue` (`src/agent-loop.ts`), the higher-level `AgentHarness` (`src/harness/agent-harness.ts`), skills, compaction, session persistence, and a portable execution-environment abstraction. This layer has no CLI, no TUI, no extension system — it's the substrate.
3. **`packages/coding-agent`** (`@earendil-works/pi-coding-agent`, the actual `pi` binary / pi.dev product) — wraps the harness with a TUI (Bubbletea-equivalent, actually a custom `@earendil-works/pi-tui`), CLI, the TypeScript **extension system**, skills/prompt-template/theme discovery, settings, and session management UX (`/resume`, `/tree`, `/fork`, etc).

This three-layer split — generic provider abstraction, generic agent-loop-plus-harness library, product-specific CLI/extension shell — has no direct analogue in kit or zero (per `kit-zero-architecture.md`), which are each a single Go module. It's closer in spirit to liam's own `Provider`/`Tool` interfaces being decoupled from the TUI, just carried much further (an entire separately-versioned harness package with no UI dependency at all).

## Tool interface

Source: `packages/ai/src/types.ts:514-519`, `packages/agent/src/types.ts:387-410`, `packages/agent/src/harness/types.ts:80-99`.

- The base `Tool` interface, defined in the **provider layer** (`pi-ai`), not the agent layer, is minimal:
  ```ts
  // packages/ai/src/types.ts:514-519
  export interface Tool<TParameters extends TSchema = TSchema> {
      name: string;
      description: string;
      parameters: TParameters;
      constrainedSampling?: false | ConstrainedSamplingConfig;
  }
  ```
  `TParameters` is a **TypeBox** (`typebox` npm package) schema — a typed schema-builder library, not hand-written `map[string]any` (kit) or hand-rolled structs (zero). TypeBox schemas double as both the JSON Schema sent to the provider and a compile-time TypeScript type (`Static<TParameters>`) for the handler's arguments — schema and type never drift apart.
- `constrainedSampling` (`ai/src/types.ts:504-512`) is a **per-tool grammar/constrained-decoding hint** with no equivalent in kit, zero, or liam's spec:
  ```ts
  export type ConstrainedSamplingConfig =
      | { type: "json_schema"; strict: "prefer" | "require" }
      | { type: "grammar"; variants: GrammarVariants };
  ```
  A tool can request either strict JSON-Schema-constrained decoding or a custom grammar for that specific tool call, when the underlying provider supports it — a lever none of liam's other prior art (kit/zero/pi-go/jcode) exposes at the tool-definition level.
- The **agent layer**'s `AgentTool` (`agent/src/types.ts:387-410`) extends `Tool` with a UI `label`, an optional `prepareArguments` compatibility shim (normalize raw args before schema validation — the analogue of jcode's tool-name/args normalization, but for arguments not names), the `execute` handler (`toolCallId, params, signal, onUpdate) => Promise<AgentToolResult>`), and a per-tool `executionMode?: "sequential" | "parallel"` override.
- `execute` takes an `AbortSignal` and an `onUpdate` streaming callback (`agent/src/types.ts:379-384`) so a long-running tool (e.g. `bash`) can push partial results (`tool_execution_update` events, surfaced live in the TUI) before final completion — liam's spec has no equivalent partial/streaming tool-result mechanism; its `Tool.Run` returns once, at the end.
- `AgentToolResult<T>` (`agent/src/types.ts:362-376`) carries `content` (text/image blocks for the model), `details: T` (structured, UI-facing, not sent to the model — the same split as zero's `Display`/`ToolOutcome`, see `kit-zero-architecture.md`), an optional `usage`, `addedToolNames` (a tool's result can **dynamically introduce new tools** into the active toolset from that point in the transcript onward — no analogue in liam/kit/zero), and a `terminate` hint (see agent loop, below).
- The harness layer adds `AgentHarnessTool` (`harness/types.ts:80-94`), which resolves an application-defined `TContext` (e.g. filesystem/shell handles, see Harness section) per turn and passes it into `execute` as a fifth argument — i.e. tools are parameterized over an injected execution context rather than closing over global state.
- Built-in tools (confirmed via `docs/settings.md:228`, the `defaultTools` setting): **`read`, `bash`, `powershell` (Windows), `edit`, `write`, `grep`, `find`, `ls`** — 7-8 tools, no `web_search`/`web_fetch` built in at all. This matches pi-go's own secondhand characterization ("7 tools") cited in `pi-go-jcode-prior-art.md`, now confirmed directly against pi.dev's own settings doc rather than through pi-go's paraphrase.

## Agent loop

Source: `packages/agent/src/agent-loop.ts` (794 lines), `packages/agent/src/types.ts:149-294` (`AgentLoopConfig`).

- Two entry points mirroring kit's `GenerateWithLoop`/`GenerateWithCallbacks` split: `agentLoop(prompts, context, config, signal, streamFn)` starts a fresh prompt; `agentLoopContinue(context, config, signal, streamFn)` resumes from existing context (used for retries — the last message must already be `user`/`toolResult`, enforced at `agent-loop.ts:75-77`).
- Both return an `EventStream<AgentEvent, AgentMessage[]>` (`agent-loop.ts:38,79`) — a typed async-iterable event stream (the `EventStream` class comes from `pi-ai`), rather than liam's chosen `iter.Seq2[Event, error]` stdlib range-over-func — same "typed event stream over synchronous callbacks" shape, different language-native primitive.
- **Two independent message-injection queues**, not present in kit/zero/liam:
  - `getSteeringMessages` (`types.ts:245`, drained in `runLoop` before each turn, `agent-loop.ts:168`) — messages injected **while the agent is still working** (e.g. the user typing a follow-up mid-stream). Tool calls from the *current* assistant turn are never skipped because of a steering message.
  - `getFollowUpMessages` (`types.ts:258`) — messages injected **only once the agent would otherwise stop** (no more tool calls, no steering messages pending), causing the outer loop to continue for another turn.
  - `QueueMode` (`types.ts:50`, `"all" | "one-at-a-time"`) controls whether a drain point injects every queued message at once or just the oldest one, deferring the rest to the next drain point.
  - liam's spec has no analogue: Escape-cancellation and `/clear` are its only mid-flight controls (per issue #41's TUI section); there's no "queue a message while the agent is mid-turn and it gets woven in without interrupting" mechanism.
- **`beforeToolCall`/`afterToolCall`** (`types.ts:278,293`) are the loop's own hook points — functionally identical in shape to liam's decided `beforeTool`/`afterTool` Hook lifecycle points (issue #41), but implemented as **in-process TypeScript callbacks passed into `AgentLoopConfig`**, not shell commands. `beforeToolCall` returning `{ block: true, reason? }` denies the call and produces an error tool result with `reason` as the message shown to the model — same shape as liam's "stderr surfaced to the model as the block reason." `afterToolCall` can override `content`/`details`/`isError`/`usage` field-by-field (explicit no-deep-merge contract documented in the type, `types.ts:74-83`).
- **`terminate`** (`AgentToolResult.terminate`, `BeforeToolCallResult.terminate`, `AfterToolCallResult.terminate`, all in `types.ts`) is a batch early-termination hint: when *every* finalized tool result in a parallel batch sets `terminate: true`, the agent stops after that batch instead of continuing. No liam/kit/zero equivalent — it's a way for a blocked/failed tool (e.g. a hard permission denial) to end the turn immediately rather than let the model attempt a different approach.
- **`ToolExecutionMode`** (`types.ts:42`, `"sequential" | "parallel"`, default `"parallel"` per the JSDoc on `toolExecution` in `types.ts:269`): tool calls from one assistant message are **preflighted sequentially** (so `beforeToolCall` decisions stay ordered and can see earlier mutations) but **executed concurrently** once allowed — `tool_execution_end` events fire in completion order, but the tool-result *messages* are still emitted later in original assistant-source order so the transcript stays deterministic regardless of which tool finished first. Per-tool `executionMode` override lets a specific tool force sequential execution even in a parallel run. liam's spec doesn't address parallel tool-call execution at all (implicitly sequential); this is a concrete design for whoever revisits that.
- `shouldStopAfterTurn`/`prepareNextTurn` (`types.ts:223,230`) let the harness request a graceful stop *before* another provider call starts (e.g. "context is getting full, stop here") or swap in replacement context/model/thinking-level for the next turn — the latter is how compaction and mid-session model switching are threaded through without the low-level loop knowing anything about either concern.
- `convertToLlm`/`transformContext` (`types.ts:154-200`) separate "prune/inject at the `AgentMessage` level" from "convert to the LLM's wire format" — `AgentMessage` is a superset of `Message` that apps can extend via TypeScript declaration merging (`CustomAgentMessages`, `types.ts:304-326`) to carry UI-only message types (artifacts, notifications) through the same transcript without polluting what's sent to the model.

## Harness layer: a portable execution environment

Source: `packages/agent/src/harness/types.ts:128-316`, `packages/agent/src/harness/env/nodejs.ts`, `packages/coding-agent/docs/containerization.md`.

- `FileSystem` and `Shell` (composed into `ExecutionEnv`, `harness/types.ts:315`) are **Result-returning, backend-independent interfaces** — every method returns `Promise<Result<T, FileError>>` / `Promise<Result<T, ExecutionError>>` (a Rust-flavored `{ok: true, value} | {ok: false, error}` union, `harness/types.ts:6`) instead of throwing, with a **stable, backend-independent error-code enum** (`FileErrorCode`: `not_found`/`permission_denied`/`is_directory`/...; `ExecutionErrorCode`: `timeout`/`shell_unavailable`/`spawn_error`/...) so calling code can branch on error kind without knowing which backend produced it.
- Exactly **one** concrete implementation ships in-repo: `harness/env/nodejs.ts` (local Node.js `fs`/`child_process`). Everything else — running tools inside a container or VM — is achieved by **swapping the `ExecutionEnv`/`FileSystem`/`Shell` implementation an extension provides**, not by a built-in sandbox flag. `docs/containerization.md` documents three concrete patterns built entirely on top of this seam:
  - **Gondolin** (`github.com/earendil-works/gondolin`, a companion project) — a local Linux micro-VM; an example extension (`examples/extensions/gondolin/`) overrides `read`/`write`/`edit`/`bash`/`grep`/`find`/`ls` to route into the VM while auth/credentials stay on the host, mounting the host cwd at `/workspace`.
  - **Plain Docker** — run the whole `pi` process in a container (`containerization.md:45-77`, with a sample `Dockerfile.pi`); simplest, but provider API keys enter the container.
  - **NVIDIA OpenShell** — a policy-controlled sandbox gateway (filesystem/process/network/credential/inference controls) that can keep raw model API keys entirely outside the sandbox by routing inference through a gateway-injected credential.
- This is a materially different answer to "how does isolation work" than any prior-art repo liam has researched: pi-go uses `os.Root` as a **hard, structural, always-on containment layer** baked into its tool constructors (per `pi-go-jcode-prior-art.md`'s finding #1); pi.dev instead exposes a **swappable execution-environment interface with zero default isolation**, pushing the actual sandboxing decision entirely to optional extensions/external tooling. Neither kit nor zero (per `kit-zero-architecture.md`) has anything like either mechanism.

## No built-in MCP, sandbox, subagents, or permission system — by design

Source: `packages/coding-agent/docs/usage.md:305-311`, `packages/coding-agent/docs/security.md` (full file).

This is pi.dev's most load-bearing architectural stance, stated by the project itself in its own words:

> "Pi keeps the core small and pushes workflow-specific behavior into extensions, skills, prompt templates, and packages. It intentionally does not include built-in MCP, sub-agents, permission popups, plan mode, to-dos, or background bash. You can build or install those workflows as extensions or packages, or use external tools such as containers and tmux." — `docs/usage.md:307-309`, with a linked design-rationale blog post ([mariozechner.at/posts/2025-11-30-pi-coding-agent](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)) not independently fetched in this pass.

And on permissions specifically, `docs/security.md` states directly (not paraphrased):

> "Pi does not include a built-in sandbox. Built-in tools can read files, write files, edit files, and run shell commands with the permissions of the pi process. Extensions are TypeScript modules that run with the same permissions." (`security.md:31-33`)
>
> "This is intentional. ... A partial in-process sandbox would be easy to misunderstand as a security boundary while still depending on the host shell, filesystem, package managers, credentials, and extension code. Real isolation needs to come from the operating system or a virtualization/container boundary." (`security.md:35`)

Confirmed against `docs/settings.md`: there is no `permissions`, `hooks`, or `sandbox` settings section at all (its full table of contents is Model & Thinking, UI & Display, Telemetry, Network, Warnings, Compaction, Branch Summary, Retry, Message Delivery, Terminal & Images, Shell, Tools, Sessions, Model Cycling, Markdown, Resources) — and no shell-command-based hook config exists anywhere in the source or docs (`grep` for `shellHook`/`"hooks"` across `docs/*.md` and `src/core/*.ts` returns nothing). Everything liam calls a "Hook" (a user-configured shell command run at a lifecycle point, no model involvement, per `CONTEXT.md`) is, in pi.dev, a **TypeScript extension callback** instead (see next section) — there's no non-code, declarative interception mechanism at all.

The one thing pi.dev *does* gate by default is **project trust** (`security.md:5-27`) — but explicitly scoped to "whether pi loads project-local settings, resources, packages, and extensions," not tool execution: *"It is not a sandbox and it does not restrict what the model can ask tools to do after you start working in a directory."* This is a narrower concept than liam's Skills trust-gate (issue #41: "project-level skill loading is trust-gated with a one-time per-project interactive prompt") generalized to cover *all* project-local dynamic config (`.pi/settings.json`, `.pi/extensions`, `.pi/skills`, `.pi/prompts`, `.pi/themes`, `.pi/SYSTEM.md`, project `.agents/skills`) under one prompt/decision, persisted per-directory in `~/.pi/agent/trust.json`, with a `project_trust` event extensions can intercept to own the decision (`extensions.md:353-368`).

**Candidate flag for liam**: liam's spec already locked a real permission-prompt system (issue #41's Permissions section) — a deliberate divergence from pi.dev's "no built-in sandbox, no built-in prompts" stance, not an oversight. Worth naming explicitly: pi.dev's bet is that the model/tool boundary is not a meaningful security boundary at all, and the only real security boundary is OS/container-level, so it doesn't try to simulate one in-process. liam's permission model is a bet in the opposite direction. Neither this research pass nor `security.md` itself claims pi.dev's position is safer — its own doc says the opposite ("a partial in-process sandbox would be easy to misunderstand as a security boundary") — but liam's spec should be understood as having consciously chosen the heavier-weight path, and pi.dev is direct primary-source evidence for the alternative philosophy, worth citing if that decision is ever revisited.

## Extension system (pi.dev's Hook/Plugin/custom-tool mechanism, all in one)

Source: `packages/coding-agent/docs/extensions.md` (3021 lines; only the first ~1374 read in this pass — event catalog and `ExtensionContext`/`ExtensionCommandContext` sections, which cover the architecturally interesting surface; `Custom Tools`/`Custom UI`/`Error Handling`/`Mode Behavior` sections past that point were not read).

- An extension is a `.ts` module exporting a default factory `(pi: ExtensionAPI) => void | Promise<void>`, loaded via **jiti** (`unjs/jiti`) so TypeScript runs with no separate compile step (`extensions.md:179`). Discovered from `~/.pi/agent/extensions/*.ts` (global) and `.pi/extensions/*.ts` (project, **only after project trust**), single-file or directory-with-`index.ts`, optionally with their own `package.json`/`node_modules` for npm deps (`extensions.md:109-271`).
- `pi.on(event, handler)` subscribes to a **documented, versioned lifecycle** that is materially larger than the ~4 points liam specced and the ~5 jcode ships (per `pi-go-jcode-prior-art.md`'s jcode section) — confirming and exceeding pi-go's secondhand "20+ in-process event hooks" claim. The catalog documented in this pass alone: `project_trust`, `resources_discover`, `session_start`, `session_info_changed`, `session_before_switch`, `session_before_fork`, `session_before_compact`/`session_compact`/`session_compact_failed`, `session_before_tree`/`session_tree`, `session_shutdown`, `before_agent_start`, `agent_start`/`agent_end`/`agent_settled`, `ui_prompt_start`/`ui_prompt_end`, `turn_start`/`turn_end`, `message_start`/`message_update`/`message_end`, `tool_execution_start`/`tool_execution_update`/`tool_execution_end`, `context`, `before_provider_headers`, `before_provider_request`, `after_provider_response`, `model_select`, `thinking_level_select`, `tool_call`, `tool_result`, `user_bash`, `input` — 30+ named events, several with a `Custom Tools`/`Custom UI` section not yet read that likely adds more.
- Two events do double duty as liam's Hook points but with materially richer contracts:
  - **`tool_call`** (`extensions.md:778-818`) — fires after `tool_execution_start`, before actual execution; **`event.input` is mutable in place** ("Mutate it in place to patch tool arguments before execution... No re-validation is performed after your mutation") — liam's `beforeTool` hook can only allow/deny, not rewrite arguments. Chains across multiple extensions in load order.
  - **`tool_result`** (`extensions.md:842-875`) — the `afterTool` analogue; also chains as middleware across extensions, each seeing the previous handler's patched result.
  - Both give the handler `ctx.signal` (the live agent abort signal) for any nested async work (e.g. an outbound `fetch` that should be cancelled on Escape) — liam's shell-command hooks have no equivalent cancellation-propagation story since a hook is a separate OS process with its own `timeoutMs`.
- `input` (`extensions.md:911-958`) is a hook point liam's spec explicitly deferred ("`userPromptSubmit`... hook points are real candidates, deferred past v1", issue #41 Hooks section) — pi.dev already has it, firing on every user submission before skill/template expansion, with three outcomes: `continue` (pass through), `transform` (rewrite text/images), `handled` (skip the agent entirely, extension handles it directly, e.g. a `ping`→`pong` command with no model call).
- `before_agent_start` (`extensions.md:530-565`) can inject a persistent session message **and/or** rewrite the system prompt for that turn, with full read access to the structured inputs Pi itself used to assemble the prompt (`systemPromptOptions`: custom prompt, selected tools, tool one-line snippets, prompt guidelines, appended-system-prompt text, cwd, loaded context files, loaded skills) — a materially deeper seam than liam's `Request.SystemPrompt` string, which extensions/hooks have no structured access to reconstruct.
- Beyond `pi.on`, `ExtensionAPI` also exposes `pi.registerTool()` (custom tools, can be called even after startup — "New tools are refreshed immediately in the same session... without `/reload`"), `pi.registerCommand()` (`/mycommand`), `pi.registerShortcut()` (keybindings), `pi.registerFlag()` (new CLI flags), and `pi.registerProvider()` (register a custom model provider/endpoint at runtime, `extensions.md:187-218`) — i.e. the extension surface covers everything liam splits across Hooks + MCP + Skills + Plugins + a hypothetical custom-provider mechanism, unified into one code-level API.
- Explicit security framing, stated the same way as for Packages (below): *"Extensions run with your full system permissions and can execute arbitrary code. Only install from sources you trust."* (`extensions.md:111`) — no capability restriction of any kind on what an extension can do once loaded; trust is binary (loaded or not) via project trust, not scoped.

## Skills: system-prompt catalog, not a tool-description catalog

Source: `packages/coding-agent/docs/skills.md`.

- Implements the [Agent Skills standard](https://agentskills.io/specification) — the same spec liam's spec targets — but **leniently**: "warning about most violations but remaining lenient," and explicitly *allows* skill names to differ from their parent directory even though the spec disallows it, because "that rule is suboptimal for shared skill directories used across multiple agent harnesses" (`skills.md:7`) — i.e. pi.dev deliberately relaxed spec conformance for cross-harness skill-directory sharing, the same interoperability goal behind liam's user story 21 ("I want liam to work with skills I already have installed for Claude Code").
- **Activation mechanism is the opposite of liam's decided design.** Per `skills.md:65-72`: at startup pi scans skill locations and extracts name+description, then **"The system prompt includes available skills in XML format"** per the agentskills.io spec's own suggested format — i.e. the full catalog sits in the base system prompt (a global cost paid every turn), not tucked inside a single tool's description the way liam decided ("the skill catalog embedded in [`activate_skill`]'s own description rather than the system prompt, to keep the base prompt minimal," issue #41 Skills section). Loading the full `SKILL.md` on activation happens via the model just calling the ordinary `read` tool on the file path already present in the XML block — there's no dedicated `activate_skill`-style tool at all; pi.dev notes models "don't always" self-activate this way, hence the `/skill:name` slash-command escape hatch for explicit force-activation (mirroring liam's own `/skill <name>` command).
- **Opt-in cross-harness interop**, not automatic scanning: unlike pi-go (which scans `.claude/skills`/`.cursor/skills` automatically per `pi-go-jcode-prior-art.md`'s finding), pi.dev requires the user to explicitly list `~/.claude/skills`/`~/.codex/skills` in `settings.json`'s `skills` array (`skills.md:44-63`) — structurally the same choice liam's spec already made (`.claude/skills/` deliberately excluded from default discovery), just implemented as an opt-in path list rather than liam's separate `.agents/skills/`+`.liam/skills/` convention.
- Discovery locations mix root-`.md`-as-skill (in `~/.pi/agent/skills/`/`.pi/skills/`) with `SKILL.md`-in-directory (everywhere) with a third convention specific to `.agents/skills/` where root `.md` files are ignored but nested ones inside grouping folders count (`skills.md:36-40`) — a more elaborate discovery-rule matrix than liam's flat "`.agents/skills/` + `.liam/skills/`, walked from git root to cwd" (issue #41).
- Skills are also installable as **pi packages** (`skills/` directories or `pi.skills` entries in a package's `package.json`) — see Packages below.

## Packages: pi.dev's Plugin equivalent — and broader

Source: `packages/coding-agent/docs/packages.md`.

- A "pi package" bundles **extensions, skills, prompt templates, and themes**, installable from npm (`pi install npm:@foo/bar@1.0.0`), git (`pi install git:github.com/user/repo@v1`), a raw URL, or a local path — directly analogous to liam's decided Plugin mechanism (git-URL or local-path install, no centralized registry) but with **no scope restriction**: liam's v1 explicitly limits plugins to `skills/` + `mcp.json` only ("No plugin-bundled tools or hooks in v1... deferred past v1," issue #41 Plugins section), while pi.dev packages bundle arbitrary extension code (full tool/hook/command surface) as the norm, not a deferred feature.
- `pi install`/`pi remove`/`pi list`/`pi update` (`packages.md:18-41`) is a real package manager, not just a fetch-and-place step: versioned npm specs are pinned and skipped by bulk updates; git packages have "pinned refs" reconciled via `pi update --all`/`--extensions`; there's a `--force` reinstall path and, notably, **`pi update --self`/`pi update` can update the `pi` CLI binary itself**, with an "experimental installer-managed" mode that stages the new release behind a lockfile and only activates it after verification, leaving the current release intact on failure (`packages.md:41`) — a self-update mechanism liam's spec explicitly put out of v1 scope ("Self-update (`liam update`)... explicitly deferred to v2+").
- Same blanket trust framing as extensions: *"Pi packages run with full system access. Extensions execute arbitrary code, and skills can instruct the model to perform any action including running executables. Review source code before installing third-party packages."* (`packages.md:20`)

## Sessions: JSONL, tree-structured, branchable — not deferred

Source: `packages/coding-agent/docs/sessions.md`.

- Sessions **auto-save** to `~/.pi/agent/sessions/`, organized by working directory, one JSONL file per session **with an explicit tree structure**, not a linear log (`sessions.md:7`). `pi -c` continues the most recent; `pi -r` opens an interactive picker (search, sort toggle, filter to named sessions, rename, delete via the `trash` CLI when available).
- Tree navigation is a first-class UX, not an implementation detail: `/tree` browses the session tree, `/fork` creates a new session from an earlier user message, `/clone` duplicates the active branch into a new session, `/compact` triggers summarization (with the extension hooks in the Events section above wired through it), `/export`/`/share` produce an HTML transcript (the latter uploaded as a private GitHub gist with a shareable link).
- liam's spec explicitly defers this whole category: "Session/conversation persistence across process restarts (confirmed as a real v2+ plan, not an open question)" — pi.dev is a concrete, shipped reference for what that could look like when liam's team gets there, specifically the **tree-not-list** structure (supporting fork/branch-compare workflows liam's own linear compaction model doesn't have a slot for) as one option among others.

## Other notable divergences worth flagging (not recommendations)

1. **TypeBox-typed tool schemas with a `constrainedSampling` grammar/strict-JSON-Schema hint per tool** (`ai/src/types.ts:504-519`) — a lever no other prior-art repo liam has researched exposes at the tool-definition level; worth a note against liam's Tool interface if grammar-constrained decoding ever becomes relevant for a specific provider.
2. **Steering-message and follow-up-message queues with an `"all"`/`"one-at-a-time"` drain mode** (`agent/src/types.ts:50,245,258`) — a real answer to "let the user keep typing while the agent works, and weave it in without a hard interrupt," genuinely different from liam's Escape-only mid-flight control.
3. **Batch-wide `terminate` hint** propagated through `AgentToolResult`/`BeforeToolCallResult`/`AfterToolCallResult` — lets a hard permission denial end the turn immediately rather than let the model retry a different approach in the same batch; liam's spec has a block/deny outcome but no analogous "and stop the whole turn" signal.
4. **Tool results that dynamically add new tools to the active toolset (`addedToolNames`)** — no analogue in liam/kit/zero; worth naming as a possible mechanism for e.g. a `connect_mcp_server` tool that then makes that server's tools callable, echoing jcode's speculative dynamic-MCP-registration plan noted in `pi-go-jcode-prior-art.md`.
5. **A portable `ExecutionEnv`/`FileSystem`/`Shell` interface with zero default sandboxing, versus pi-go's `os.Root` hard-jail default** — two real, shipped, opposite answers to "how does isolation work" from projects that otherwise share a name and lineage; useful as bracketing prior art for any future liam sandboxing ticket, alongside the already-flagged `os.Root` candidate from `pi-go-jcode-prior-art.md`.
6. **No built-in MCP, sandbox, subagents, or permission system at all — stated as deliberate philosophy, not a gap** (`docs/usage.md:305-311`, `docs/security.md`) — the single most direct primary-source counterpoint to liam's own decided direction (issue #41 ships a permission-prompt system and MCP support in v1). Not a reason to reconsider either decision, but the clearest "here is the alternative philosophy, argued by its own authors" reference liam's research has surfaced so far.
7. **Extensions as the single unified mechanism for what liam splits into Hooks + custom tools + custom commands + custom providers** — with `tool_call`'s in-place argument mutation and `input`'s three-way `continue`/`transform`/`handled` outcome being strictly more expressive than liam's shell-command Hook contract (allow/deny only, no argument rewriting, no full request interception). Liam's stdlib-first, no-embedded-language-runtime constraint (issue #41: "strongly prefer stdlib") is presumably why liam didn't take this path — TypeScript-via-jiti is a runtime dependency pi.dev's team clearly considers a acceptable; worth naming explicitly as a deliberate tradeoff rather than an unconsidered gap, since it's the most powerful mechanism found across every prior-art repo researched so far (kit, zero, pi-go, jcode, pi.dev).
8. **A real package manager for the harness itself**, including self-update with staged/verified rollback (`pi update --self`) — liam's spec defers self-update entirely; pi.dev's staged-lockfile-behind-verification approach is a concrete reference if that ticket is ever picked up.
9. **JSONL sessions with an explicit branch/tree structure** (fork, clone, tree-navigate) rather than a linear log — a structurally different answer than "just persist the flat transcript" for liam's deferred session-persistence work.
