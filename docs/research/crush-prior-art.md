# Research: charmbracelet/crush as prior art for liam's TUI and harness architecture

This is prior-art research triggered by a direct user request, parallel to the existing pi-go/jcode research (`docs/research/pi-go-jcode-prior-art.md`) — not tied to any GitHub issue. Crush is Charm's own coding-agent CLI, built by the same organization (charmbracelet) whose Bubble Tea v2 and Lipgloss v2 liam's own TUI is built on, so it's evaluated here both as a general harness peer and, specifically, as liam's closest available *Go+Bubble Tea* TUI-architecture peer — a comparison pi-go (Google ADK Go) and jcode (Rust) couldn't offer.

- `github.com/charmbracelet/crush` — cloned at commit `e3c970336d7ca889b75dd9bf8c1c4ffd42d65396` in a shallow clone taken 2026-09-02. Go module `github.com/charmbracelet/crush`, `go.mod` requires Go 1.27.0.

## crush: what it is

Source: `README.md:1-22`.

"Your new coding bestie, now available in your favourite terminal... Your tools, your code, and your workflows, wired into your LLM of choice." README's feature list: multi-model (built-in providers plus custom OpenAI-/Anthropic-compatible endpoints), mid-session model switching with context preserved, multiple concurrent sessions per project, LSP-derived context, MCP extensibility (`http`, `stdio`, `sse`), and "first-class support in every terminal" across macOS/Linux/Windows/Android/BSD.

Crush has grown considerably past a simple TUI wrapper: it now ships a client/server split (`internal/server`, `internal/client`, `internal/backend`, `internal/workspace`) so multiple TUI clients can attach to one running agent process and share session state, an embedded POSIX shell interpreter (`mvdan.cc/sh`) used for both the `bash` tool *and* its own config language, a SQLite-backed persistence layer, a full Agent Skills implementation, preliminary Claude-Code-compatible hooks, LSP client integration, and its own design-token color system (`charmtone`) layered under a custom hybrid rendering pipeline. This is a categorically larger, more mature project than liam (or than pi-go/jcode) — closer to "an IDE-grade agent runtime" than "a minimal harness" — so treat it as a rich source of *individual* patterns to weigh, not as an architecture to adopt wholesale.

## crush: TUI architecture (Bubble Tea v2 / Lipgloss v2 / Ultraviolet)

Source: `internal/ui/AGENTS.md:1-240`, `internal/ui/dialog/dialog.go:1-46`, `internal/ui/list/item.go:21-36`, `internal/ui/chat/messages.go:53-68`, `internal/ui/chat/tools.go:45-60`, `internal/ui/styles/themes.go:1-32`.

Crush's own `internal/ui/AGENTS.md` is a written architecture doc for exactly the layer liam's own `internal/tui` occupies — a rare case of the peer project documenting its own conventions in a form directly comparable to how liam would describe its own.

- **Single-model, non-Elm sub-components.** `UI` (the top-level struct, described in `AGENTS.md:36-54`) is "the sole Bubble Tea model." Every sub-component — `Chat`, `List`, `Attachments`, `Completions`, `Sidebar` — is a plain stateful struct with imperative methods (`HandleMouseDown()`, `ScrollBy()`, `SetMessages()`), not a nested `tea.Model` with its own `Update()`. `AGENTS.md:56-77` states this explicitly as the pattern to follow: "Expose imperative methods for state changes (not `Update(tea.Msg)`)... Let the main `UI.Update()` decide when and how to call into the component." liam's `internal/tui/tui.go` follows the same top-level shape — one `Model` with a giant `Update(msg tea.Msg)` switch (`tui.go:285`) and value-receiver methods — and liam's popup logic (`internal/tui/popup.go`) is likewise not its own `tea.Model`, just functions operating on the parent `Model`'s state. This is a case where liam's simpler, hand-rolled design and crush's much larger one arrived at the *same* top-level convention independently — worth noting as validation rather than a gap.
- **Hybrid rendering, not pure string concatenation.** Crush's rendering pipeline (`AGENTS.md:22-35`) is a step beyond liam's: the top-level `UI` model owns a `uv.ScreenBuffer` (from `github.com/charmbracelet/ultraviolet`, the same `uv` package liam already pulls in indirectly per `go.mod`), and components draw into sub-rectangles (`uv.NewStyledString(str).Draw(scr, rect)`) via a rectangle-based `uiLayout` struct (`layout.header`, `layout.main`, `layout.editor`, `layout.sidebar`, `layout.pills`, `layout.status`); sub-components like `list.List` still render to plain strings that get painted onto the buffer. `View()` then flattens the buffer to a string for Bubble Tea. liam's `tui.go` (`renderTranscript()` at `tui.go:815`, `View()` at `tui.go:832`) is pure string-based — layout via Lipgloss joins, not a screen buffer — which is simpler but has no equivalent of "draw a sub-component into a rectangle independent of paint order." Worth flagging as the main structural TUI difference: crush's screen-buffer approach exists specifically to support the dialog-overlay stack (below) and the interleaved sidebar/pills/status regions crush's richer layout needs; liam's simpler chrome (transcript + input + status block per `CONTEXT.md`'s Transcript/Popup vocabulary) may not need it, but it's the concrete alternative if liam's layout ever grows more regions.
- **Dialogs as a real interface with an explicit overlay stack.** `dialog.Dialog` (`dialog/dialog.go:33-45`) requires `ID() string`, `HandleMsg(msg tea.Msg) Action`, and `Draw(scr uv.Screen, area uv.Rectangle) *tea.Cursor`; an `Overlay` manages a *stack* of dialogs (push/pop/contains), and "Dialogs draw last and overlay everything else" (`AGENTS.md:156-164`). Crush has ~30 distinct dialog implementations (`internal/ui/dialog/*.go`: models, sessions, commands, permissions, API key, OAuth, filepicker, reasoning, quit, MCP auth, AWS SSO, question forms, etc.) all implementing this one interface, so any dialog composes with any other on the stack. liam's spec, per `CONTEXT.md`'s **Popup** term, has exactly two non-stacking popups (`@`-mention, `/`-command) with no generic `Dialog` interface or stack — a much narrower need today, but if liam ever grows a second *kind* of transient UI beyond the two popups (a model picker, a permission-prompt dialog, a session switcher), crush's `Dialog`/`Overlay` shape is the direct reference for how to generalize without hardcoding N ad hoc popup types.
- **A written style guide for the exact bugs Lipgloss v2 width math causes.** `AGENTS.md:165-192` codifies dialog-rendering rules earned the hard way: size to the *content area* (`m.width - t.Dialog.View.GetHorizontalFrameSize()`), never `Margin` inside a bordered box (only `Padding`), render styled segments individually and concatenate rather than wrapping one big string in one style ("An inner segment's reset code drops the outer color for everything after it"), and clamp dialog width/height to the drawable area so dialogs don't overflow small terminals. These are Lipgloss v2-specific footguns, directly relevant to liam's own Lipgloss v2 usage regardless of the screen-buffer-vs-string-rendering difference — concrete, transferable advice liam's TUI code should hold itself to even without adopting any of crush's larger architecture.
- **Layered interface composition for list items**, not one god-interface. `list.Item` is the two-method base (`Render(width int) string`, `Version() uint64` — `list/item.go:21-30`); `MessageItem` adds `list.RawRenderable` + `Identifiable`; `ToolMessageItem` adds tool-call/result/status methods (`chat/tools.go:45-55`); optional capabilities (`Focusable`, `Highlightable`, `Expandable`, `Animatable`, `Compactable`, `KeyEventHandler`) are separate opt-in interfaces components implement only if they need them. A **central factory** (`NewToolMessageItem` in `chat/tools.go`) routes each tool name to its own renderer type, with one file per tool-family (`chat/bash.go` for Bash/JobOutput/JobKill, `chat/file.go` for View/Write/Edit/MultiEdit/Download, `chat/search.go` for Glob/Grep/LS/Sourcegraph, `chat/fetch.go`, `chat/agent.go`, `chat/mcp.go` for the `mcp_`-prefixed family, `chat/generic.go` as the fallback for unrecognized tools — table at `AGENTS.md:133-146`). This "one file per tool-family renderer, routed by name, generic fallback for anything unrecognized (including MCP tools)" pattern is a direct, reusable idea for however liam's transcript renders tool calls per-Tool today — worth checking against liam's own transcript-rendering code for whether it already does this or has one monolithic renderer switch.
- **Theming**: crush's default theme is `CharmtonePantera()` (`styles/themes.go:34-50`), built from `github.com/charmbracelet/x/exp/charmtone` — Charm's own design-token color palette (named colors like `charmtone.Charple`, `charmtone.Dolly`, `charmtone.Pepper`) rather than raw hex. Distinctively, **theme selection is provider-keyed**: `ThemeForProvider(providerID string)` (`themes.go:22-31`) picks a different theme depending on which model provider is active (a `hyper`-specific theme for Charm's own Hyper provider, `CharmtonePantera` as the fallback for everyone else) — the UI's palette changes when you switch providers. liam's `internal/theme/theme.go` is a fixed two-palette (Catppuccin Frappe/Latte) system selected only by dark/light mode (`theme.go:33-45`), with no per-provider variation and no design-token library — simpler and arguably more predictable, but worth naming as a deliberate scope difference: crush treats the active provider as a branding signal in the UI, liam does not.

## crush: tool interface

Source: `go.mod:10`, `internal/agent/tools/tools.go:1-105`, `internal/agent/tools/view.go:1-80`, `charm.land/fantasy@v0.41.3/tool.go:91-176`, `charm.land/fantasy@v0.41.3/content.go:488-495`.

- Crush, like pi-go (per the existing research) and like the "kit" project referenced there, **does not define its own `Tool` interface** — it builds on Charm's own `charm.land/fantasy` agent framework (`go.mod:10`, pinned `v0.42.1`; a slightly older `v0.41.3` happened to be present in the local Go module cache and was read directly for interface shapes). `fantasy.AgentTool` (`tool.go:93-98`) is the interface: `Info() ToolInfo`, `Run(ctx, ToolCall) (ToolResponse, error)`, `ProviderOptions()`/`SetProviderOptions()`. `fantasy.NewAgentTool[TInput](name, description, fn)` (`tool.go:102-117`) is "the recommended way to create tools" — a generic constructor that reflects a typed Go struct into a JSON schema automatically (`schema.Generate(reflect.TypeOf(input))`), rather than a struct manually implementing an interface by hand. Crush's own per-tool files (`internal/agent/tools/view.go`, `bash.go`, `edit.go`, etc.) are thin wrappers around this: typed `Params` structs with `json`/`description` struct tags (e.g. `ViewParams` at `view.go:47-51`), an embedded `.md.tpl` file for the tool description rendered via `html/template` (`tools.go:86-96`), and a call into `fantasy.NewAgentTool`.
- This is a directly relevant confirmation of a pattern already flagged in the pi-go research: **liam is the outlier here, not the norm** — both pi-go (Google ADK Go) and crush (Charm's own `fantasy`) delegate the Tool/Provider/agent-loop primitives to an external framework rather than hand-rolling them in the harness. liam's `CONTEXT.md` defines **Tool** as "implemented in Go and compiled into the harness" with no mention of an external tool-framework dependency, matching what liam's `go.mod` shows (no `fantasy`, no ADK — only `charm.land/bubbletea`/`bubbles`/`lipgloss`, the OpenRouter Go SDK, and the MCP Go SDK). liam's approach is architecturally closer to jcode's hand-rolled `Tool` trait than to either Go-language peer's framework-delegated approach — worth naming explicitly as liam's considered position (a stdlib-first, dependency-minimal harness) rather than an oversight, especially now that *two* separate organizations building Go coding-agent CLIs (Google's pi-go author, and Charm itself) both reached for a third-party agent-framework library instead.
- `fantasy.ToolResponse` (`tool.go:32-42`) carries a `StopTurn bool` field, and crush's `NewPermissionDeniedResponse()` (`tools.go:64-70`) sets it: "returns a tool response indicating the user denied permission, with StopTurn set so the agent loop does not retry." This is a clean, narrow mechanism — a tool response can unilaterally end the agent's turn rather than let the model retry or route around a denial — worth checking against how liam's spec handles a denied permission's effect on the agent loop.
- Crush's `getContextValue[T any]` generic helper (`tools.go:33-42`) and its four typed context keys (`SessionIDContextKey`, `MessageIDContextKey`, `SupportsImagesContextKey`, `ModelNameContextKey` — `tools.go:20-29`) are how tool implementations reach session/model context without it being part of the `fantasy.AgentTool` signature — a plain Go `context.Context` convention, not a framework feature. Unremarkable but a clean small pattern if liam's own tool functions need equivalent ambient context (session ID, active model name) without widening the Tool interface's function signature.

## crush: provider abstraction

Source: `charm.land/fantasy@v0.41.3/provider.go:1-12`, `charm.land/fantasy@v0.41.3/model.go:256` (referenced, not read in full), `README.md:194-231,239-245`, `internal/config/config.go:88-113`.

- `fantasy.Provider` is a two-method interface: `Name() string` and `LanguageModel(ctx, modelID string) (LanguageModel, error)` (`provider.go:7-11`) — again, not crush's own type, but `fantasy`'s. Crush's `ProviderConfig` (`config.go:88-113`) is the *user-facing config* wrapping this: `ID`, `Name`, `BaseURL`, `Type` (a `catwalk.Type` enum — `openai`/`anthropic`/etc.), `APIKey` (with shell-expansion support, `$VAR`/`$(cmd)`), `OAuthToken`, `Disable`, `SystemPromptPrefix`, and `ExtraHeaders`/`ExtraBody` for provider-specific passthrough.
- **Catwalk**: crush's default model/provider list is not hardcoded — it's fetched from `charmbracelet/catwalk`, described in the README as "a community-supported, open source repository of Crush-compatible models" (`README.md:243`), auto-updated at startup unless disabled (`CRUSH_DISABLE_PROVIDER_AUTO_UPDATE`), with a `crush update-providers` command to pull from a custom URL or reset to the embedded snapshot (`README.md:883-935`). This is a materially different model-catalog strategy than liam's: liam's spec (per `CONTEXT.md`'s **Provider** definition) treats OpenRouter's own auto-routing as the mechanism for "which model backs a request," with OpenRouter itself as the catalog; crush instead maintains its own cross-provider model/pricing/capability database as a separate open-source project and layers many first-class provider adapters (Anthropic, OpenAI, Gemini, Bedrock, Vertex AI, Azure OpenAI, and 20+ OpenAI-compatible aggregators per the README's env-var table at `README.md:202-231`) on top of it, rather than routing everything through one aggregator. Worth flagging as an alternative to "OpenRouter as the single default provider" if liam's spec ever widens past that.
- **Provider auth breadth mirrors what the pi-go/jcode research already flagged**: crush supports env-var API keys, in-TUI paste (`ctrl+l` model picker), OAuth (its own Hyper provider, GitHub Copilot, MCP OAuth), and full AWS/GCP credential-chain delegation for Bedrock/Vertex (`README.md:740-805`) — reinforcing the existing "per-provider subscription OAuth" candidate-idea entry from the pi-go/jcode research (item 8 there) rather than adding a new one.

## crush: config format and locations

Source: `README.md:247-343,482-505`, `docs/config/README.md:1-40`, `internal/shellconfig/load.go:1-70`, `internal/shellconfig/hook.go:10-35`, `internal/config/config.go:711-739`.

This is the single largest design divergence from liam found in this pass. Crush's config is **not a static file format at all** — it's a Bash DSL:

- `crushrc` "is just Bash with some Crush-specific builtins. It's a lot like a `.bashrc`, just for your Crush" (`README.md:256-259`). Crush embeds its own POSIX shell interpreter (`mvdan.cc/sh` — the same one backing the `bash` tool and hooks) and runs `crushrc` through it at startup, with builtins like `provider add`, `model add`, `permissions allow`, `mcp add`, `lsp add`, `hook add`, `option ...` that mutate an in-memory `ConfigBuilder` (`internal/shellconfig/builder.go`, referenced from `hook.go:24-64`) rather than parse structured data. The builtins are declarative flag specs (`hookAddFlags []flagSpec` at `hook.go:39-44`) applied via a shared `applyFlags` helper. The script's accumulated builder state is marshaled to JSON at the end (`load.go` doc comment: "returns its config as a single JSON object... merges with any other config files") and merged with other config sources — so the *runtime* config model is still a JSON tree, but the *authoring* surface is executable shell, not JSON/JSONC. A `loadTimeout` of 30s (`load.go:19-20`) bounds a single `crushrc` execution "so a script that blocks... must not be able to wedge the whole store."
- The legacy path — a plain `crush.json`/`.crush.json` (with a `$schema` field, per the `env` example at `README.md:336-343`) — "is still supported, but it should be considered deprecated" (`README.md:301-302`); crush even ships a builtin skill so the agent itself can convert an old JSON config to `crushrc` on request. Config precedence is `./.crushrc` > `./crushrc` > `~/.config/crush/crushrc` on Unix, respecting XDG (`README.md:288-299`); ephemeral runtime state (distinct from config) lives separately at `~/.local/share/crush/crush.json`.
- This is a striking contrast to liam's spec's JSONC decision (per the pi-go/jcode doc's citation of that choice at `pi-go-jcode-prior-art.md:30`). Where pi-go chose plain JSON and liam chose JSONC specifically to allow comments in an otherwise-static format, crush went further and made the config format *itself executable*, explicitly modeled on `.bashrc` — trading static analyzability (you can't just parse `crushrc` and know the resulting config without running it) for expressiveness (conditionals, host-specific branches, secret-manager shell-outs like `--header Authorization "Bearer $(op read 'op://my-secret-key')"` in the README's own example at `README.md:278-282`). Crush's own docs are explicit about the resulting trust boundary: "Both `crushrc` and `crush.json` are trusted code; `crushrc` runs in a full shell, and any `$(...)` in `crush.json` runs at load time. Don't launch Crush in a directory whose config you haven't reviewed" (`README.md:322-327`) — i.e. even crush's "static" JSON format isn't fully static, since values get shell-expanded. This is worth flagging as a considered alternative to liam's JSONC choice, with the explicit security tradeoff crush's own maintainers document, not a recommendation to follow it — liam's simpler "config is inert data" model avoids exactly the trust-boundary problem crush's docs call out.
- **Hooks config shape**: `Hooks map[string][]HookConfig` keyed by event name (`config.go:733`), where `HookConfig` (`config.go:681-690`) is `Name` (display), `Matcher` (regex against tool name, empty = match all), `Command`, `Timeout` (seconds, default 30). This is a third distinct shape from the two the pi-go/jcode research already compared (liam's object-of-arrays-by-lifecycle-point vs. pi-go's flat array with an `Event` field) — crush's is a map-of-arrays-by-event, structurally similar to liam's but confirmed here as another working precedent for that shape specifically.
- **MCP config**: `MCPConfig` (`config.go:193-233`) supports `stdio`, `http`, and `sse` transports (liam's v1 spec is stdio-only, matching pi-go's and jcode's noted scope), full OAuth 2.1 with dynamic client registration or pre-registered client credentials (`OAuth`, `OAuthClientID`, `OAuthClientSecret`, `OAuthCallbackPort`), and a `Sessionless` flag to work around HTTP MCP servers (e.g. GitHub's own MCP server) that don't issue an `Mcp-Session-Id` and would otherwise break crush's list-changed notification stream (`config.go:204-215`) — a specific, narrow interop bug/workaround worth remembering if liam's own (currently out-of-scope) future HTTP MCP transport work ever hits the same GitHub-MCP-server behavior.
- **Global context files**: crush auto-includes `~/.config/crush/CRUSH.md` (Crush-specific instructions) *and* `~/.config/AGENTS.md` (generic, tool-agnostic instructions meant to be shared across multiple agentic CLIs) as two separate global context files (`README.md:482-493`), customizable via repeatable `option global-context-path`. liam's **Identity preamble** concept (`CONTEXT.md`) plus its project-level `AGENTS.md`/`LIAM.md` discovery is narrower — no global (`~`-scoped) context-file convention currently. Worth flagging as a gap: a user with several agentic CLIs installed might want one shared `~/.config/AGENTS.md` all of them read, which liam's spec doesn't currently address for global (non-project) instructions.

## crush: session persistence

Source: `internal/session/session.go:1-70`, `internal/db/connect.go:1-40`, `internal/db/connect_modernc.go:1-20`, `internal/db/connect_ncruces.go:1-20`, `go.mod:41,49-50,56,76`.

- Crush persists sessions to **SQLite**, not JSONL (contrast with pi-go's JSONL-with-branching noted in the existing research). Migrations are managed with `pressly/goose` embedded from `internal/db/migrations/*.sql` (`connect.go:17,33-36`), and query code is presumably `sqlc`-style generated (`internal/db/sessions.sql.go`, `messages.sql.go`, `files.sql.go`, `stats.sql.go`, `querier.go` — a `Querier` interface over typed generated methods, not raw SQL scattered through the codebase).
- **Two SQLite drivers, selected by build tag**: `connect_modernc.go` (build tag: darwin/freebsd/linux/windows on standard architectures) uses `modernc.org/sqlite`, a pure-Go, cgo-free SQLite implementation; `connect_ncruces.go` (the negated build-tag complement — anything not covered above) falls back to `github.com/ncruces/go-sqlite3`, which runs SQLite compiled to WASM via a Go WASM runtime, for architectures the pure-Go driver doesn't support. Both are `database/sql` drivers, so the rest of the codebase is driver-agnostic. This is a notable engineering pattern — full SQLite functionality with zero cgo dependency on every supported platform — directly relevant if liam ever needs durable structured session storage beyond whatever it uses today; the pi-go/jcode research didn't surface a SQLite-based peer at all, so this is new prior art specifically for "how do you ship real SQLite in a single static Go binary."
- Session-level pragmas are tuned for a single-writer desktop app: WAL journal mode, `synchronous=NORMAL`, `secure_delete=ON`, a 30s busy timeout, 4096-byte pages, 8MB negative cache size (`connect.go:18-27`) — a reasonable reference pragma set if liam ever adopts SQLite for session storage.
- The `Session` struct itself (`session.go:50-63`) carries `PromptTokens`/`CompletionTokens`/`Cost`/`EstimatedUsage` and a `Todos []Todo` field directly on the session row (with `TodoStatus` enum `pending`/`in_progress`/`completed` — `session.go:19-25,34-48`) — i.e. crush's session-level "todo list" tool state is persisted as a first-class column, not reconstructed from message history. liam's spec doesn't currently define a todo/task-list tool; if one is ever added, storing todo state as session-level structured data (rather than re-deriving it from the transcript on load) is the pattern crush uses.

## crush: skills

Source: `internal/skills/skills.go:1-50`, `internal/skills/catalog.go:1-80`, `internal/agent/prompt/prompt.go:173-216`, `internal/skills/skills.go:297-322`, `internal/agent/tools/view.go:63,94-107,266-267,444-485`, `README.md:551-634`.

- Crush implements the same **Agent Skills open standard** (agentskills.io) liam's own **Skill** definition cites (`internal/skills/skills.go:1-2`: "Package skills implements the Agent Skills open standard. See https://agentskills.io for the specification"). A `Skill` (`skills.go:36-49`) is parsed from a `SKILL.md` with YAML frontmatter: `name`, `description`, `user-invocable`, `disable-model-invocation`, `license`, `compatibility`, `metadata`.
- **Activation mechanism is materially different from liam's `activate_skill` tool.** Crush does *not* have a dedicated skill-activation tool. Instead: (1) at prompt-assembly time, the full catalog of available skills (builtin + discovered, deduplicated, filtered by disabled-list) is serialized as XML and injected directly into the system prompt — `skills.ToPromptXML` (`skills.go:297-322`) emits an `<available_skills>` block with `<name>`/`<description>`/`<location>`/`<type>` per skill, built in `internal/agent/prompt/prompt.go:173-216`; and (2) the model loads a skill's full content by calling the ordinary **`view`** tool against the skill's `<location>` path — `view.go` special-cases paths under `skills.BuiltinPrefix` (`view.go:107,444-446`) and tags the response `ViewResourceType: "skill"` (`view.go:63,266-267,484-485`) so the TUI can render it distinctly, but there is no separate tool call. This is the same overall shape liam's spec deliberately avoided (per the existing pi-go/jcode research item 10, contrasting jcode's embedding-based auto-injection against liam's enum-constrained `activate_skill` tool) but via a *third* mechanism neither prior document covered: a static XML catalog inline in the system prompt (paying the token cost liam's `activate_skill`-tool-description approach was designed to avoid) plus reuse of an existing file-reading tool for retrieval (avoiding a dedicated activation tool, unlike liam's `activate_skill(name)`). Worth flagging as a third concrete alternative on the same spectrum: liam (catalog-in-tool-description, dedicated activation tool) vs. jcode (embedding-based, no catalog at all) vs. crush (catalog-in-system-prompt, retrieval via existing `view` tool).
- **Discovery locations are broader than liam's and explicitly include Claude Code's directory** — the opposite choice from what liam's spec made. Global: `$CRUSH_SKILLS_DIR`, `$XDG_CONFIG_HOME/agents/skills` (liam's own convention's location, notably), `$XDG_CONFIG_HOME/crush/skills`, `~/.agents/skills/`, and **`~/.claude/skills/`** (README.md:558-567). Project-relative: `.agents/skills`, `.crush/skills`, **`.claude/skills`**, and **`.cursor/skills`** (`README.md:570-576`). This directly reinforces the pattern the pi-go research already flagged for pi-go's `.claude/skills`/`.cursor/skills` scanning (item 9 in that doc's summary) — crush independently made the same choice pi-go made and liam's spec explicitly declined ("no scan of `.claude/skills/`"). Two of three Go-ecosystem peers researched now scan Claude Code's skill directory directly; liam remains the outlier by design, worth re-flagging with this additional data point.
- **User-invocable skills as slash-command-adjacent UI**: a skill with `user-invocable: true` in its frontmatter appears in crush's command palette (`ctrl+p`) prefixed `user:`/`project:` by source (`README.md:602-619`), and `disable-model-invocation: true` hides it from the model's catalog while keeping it user-invocable (`README.md:623-634`) — i.e., crush's frontmatter has an explicit two-axis visibility control (model-invocable × user-invocable) that liam's spec's simpler `/<skill-name>` force-activation (per `CONTEXT.md`'s **Slash command** definition, "bypasses model judgment") doesn't currently distinguish; liam's model already supports the *effect* (a slash command always force-activates regardless of the model's catalog) but has no config knob for a skill author to say "never let the model auto-trigger this one." Worth a note as a possible frontmatter addition if that need arises.
- Crush ships a **`pi audit`-adjacent but different idea**: rather than a security scanner, crush ships a *self-configuring* builtin skill (`internal/skills/builtin/crush-config`, `crush-hooks`) that lets the agent write its own `crushrc`/hooks from natural language ("Crush ships with a builtin skill for configuring itself... you can just tell what you want it to configure" — `README.md:249-251`, `docs/hooks/README.md`'s "Crush ships a builtin `crush-hook` skill"). This is a "skills that configure the harness itself" pattern with no equivalent flagged in the pi-go/jcode research and none currently in liam's spec — a different, complementary idea to that research's item 3 (skill-content security scanning): instead of auditing skill content for danger, crush uses skills as a *config-authoring* tool.

## crush: hooks

Source: `docs/hooks/README.md:1-260`, `internal/permission/permission.go:16-36,181-202`.

- **"Hooks are Claude Code-compatible"** is stated directly in the docs (`docs/hooks/README.md:16`), and crush currently implements exactly **one** event, `PreToolUse` (`README.md:26-27`: "Crush currently supports just one hook, `PreToolUse`, with plans to support the full gamut"), matching liam's spec's own `beforeTool` hook point as (per the existing research) the one both liam and jcode treat as the synchronous/blocking case. Event names are case- and separator-insensitive (`PreToolUse`/`pretooluse`/`pre_tool_use` all match — `README.md:184-187`).
- **Contract**: exit 0 or JSON `{"decision":"allow"}` = allow (and permission-pre-approves — see below); exit 2 or `{"decision":"deny"}` = block; silence/no decision falls through to the normal permission prompt (`README.md:216-222`). This is a direct match to the jcode `pre_tool` contract already documented in the pi-go/jcode research (exit 0 = allow, exit 2 = block, hook stderr surfaced to the model) — crush is a second independent confirmation of that exact exit-code convention, worth citing alongside jcode's for whoever finalizes liam's own hook contract.
- **Parallel execution, config-order resolution, deny-wins**: "Hooks run in parallel for speed, but their results compose in config order for determinism" (`README.md:37-38`); when multiple hooks match one tool call, they're deduplicated by identical `command` and run concurrently, then aggregated "deny wins over allow, allow wins over none; `updated_input` patches shallow-merge in order" (`README.md:214-222`). This is a materially more specified multi-hook-per-event resolution policy than either liam's spec or the jcode doc mention (jcode's doc, per the existing research, only covers per-hook timeout/failure semantics, not multi-hook aggregation order) — a concrete answer to "what happens when two `PreToolUse` hooks disagree" that liam's Hooks section doesn't currently specify.
- **Hook approval short-circuits the permission prompt directly in code**, not just in the docs: `permission.WithHookApproval(ctx, toolCallID)` (`permission.go:21-26`) stamps a context key, and `permissionService.Request` (`permission.go:192-202`) checks `hookApproved(ctx, opts.ToolCallID)` before doing anything else — an allow decision from a hook "skip[s] the prompt entirely" but still "publish[es] a granted notification so the UI and audit subscribers see the outcome," i.e. the permission-audit trail still records the grant even though no human was asked. Directly relevant to liam's own Permissions/Hooks interaction: this is the concrete implementation shape (a context-scoped, tool-call-ID-keyed pre-approval flag threaded from the hook runner into the permission service) for "an allow-deciding hook bypasses the prompt," which liam's spec states as a requirement but (per the pi-go/jcode research) doesn't specify a failure-mode or wiring pattern for.
- **Scope carve-out for sub-agents**: "`PreToolUse` only fires on the top-level agent's tool calls. Sub-agents... run without hook interception so a single delegated turn doesn't trigger your hook N times. The outer sub-agent tool call itself is hooked" (`README.md:191-195`). liam's spec doesn't currently define a sub-agent/task-tool concept at all, so this is forward-looking rather than an immediate gap — but worth remembering if liam ever adds one, since "hook the outer delegation call, not every inner call the delegate makes" is a non-obvious design decision crush already made and documented the reasoning for.
- **Execution model reuses the `bash` tool's own interpreter** (`mvdan.cc/sh`) for hook commands, with OS-portable shebang handling (a documented "permissive shebang fallback": if a shebang's absolute interpreter path doesn't exist — e.g. `#!/bin/bash` on Windows — crush falls back to a `PATH` lookup of the base name, logging the fallback — `README.md:139-144`) and guaranteed `CRUSH=1`/`AGENT=crush`/`AI_AGENT=crush` env vars set identically by both the hook runner and the `bash` tool so a script can detect "am I running under an AI agent" the same way in either context (`README.md:130-135`). liam's spec presumably runs hooks via `os/exec` directly rather than through an embedded shell interpreter; crush's choice to route hooks and the `bash` tool through the *same* interpreter is what buys it that env-var/shebang-handling consistency for free — worth noting as the reason behind the consistency rather than something to copy outright (liam doesn't have an embedded shell interpreter and probably shouldn't add one solely for this).

## crush: MCP

Source: `README.md:362-441`, `internal/config/config.go:193-233`, `go.mod:49` (`github.com/modelcontextprotocol/go-sdk`).

- Same official `github.com/modelcontextprotocol/go-sdk` dependency liam's own `go.mod` already uses (`go.mod:11` in liam) — both harnesses build MCP client support on the same upstream SDK rather than hand-rolling the protocol, so this is confirmation of shared tooling rather than a new pattern.
- Transport support (`stdio`/`http`/`sse`) and MCP OAuth 2.1 (dynamic client registration, or pre-registered client ID/secret for servers like GitHub/Slack that don't support dynamic registration) are already covered above under Config; both go beyond liam's v1 stdio-only scope, consistent with what the pi-go/jcode research already flagged as a deferred v2+ item for liam (that research's item 9 area) — crush is a second/third confirmation, not a new finding.
- `disabled_tools`/`enabled_tools` per-MCP-server allow/deny lists (`config.go:200-201`) — a fine-grained tool-visibility control at the server level, on top of whatever coarser MCP-server-level enable/disable liam's spec has; worth checking whether liam's spec allows filtering *which* tools of a connected MCP server are exposed, versus only connecting/disconnecting the whole server.

## Summary: candidate ideas worth surfacing (not recommendations)

Per the same framing as the existing pi-go/jcode research — these are flagged as things worth someone's attention against liam's already-decided spec, not adoption decisions:

1. **TUI: single-model/imperative-sub-component pattern and Lipgloss v2 width-math gotchas** (`internal/ui/AGENTS.md`) — liam's `tui.go` already independently follows the "one `tea.Model`, imperative sub-components" shape crush's own architecture doc prescribes; the padding-vs-margin, per-segment-styling, and content-area-sizing rules in that doc are directly transferable defensive conventions for any further Lipgloss v2 work in liam's TUI, adoptable without any of crush's larger architecture.
2. **A generic `Dialog`/`Overlay` stack interface** (`dialog/dialog.go`) as the reference shape if liam's two hardcoded Popup types (`@`-mention, `/`-command) ever need to generalize to more than two, or to stack (e.g. a confirmation dialog opening from within a popup).
3. **One-file-per-tool-family transcript renderers routed by a central factory, with a generic fallback for unrecognized/MCP tools** (`chat/tools.go`, `AGENTS.md:121-146`) — worth checking against however liam's transcript currently renders tool calls.
4. **Provider-keyed theming** (`styles/themes.go`) as an alternative to liam's fixed dark/light-only theme selection, if a future provider-branding requirement arises — noted as a scope difference, not a gap.
5. **liam is the outlier among Go coding-agent harnesses in hand-rolling its own Tool/Provider interfaces** rather than building on an external agent framework — both pi-go (Google ADK Go) and crush (`charm.land/fantasy`) delegate this layer. Worth naming explicitly as liam's considered, stdlib-first position now that it's 2-for-2 against Go peers rather than a novel choice.
6. **A `StopTurn` flag on tool responses** (`fantasy.ToolResponse`) letting a single tool call unilaterally end the agent's turn (used for permission denial) — worth checking against how liam's spec handles a denied permission's effect on the agent loop.
7. **An executable (Bash-DSL) config format, `crushrc`**, as the most extreme alternative on the config-format spectrum from liam's static JSONC — trades static analyzability for scripting power, with an explicit, documented trust-boundary cost ("both `crushrc` and `crush.json` are trusted code") that liam's inert-JSONC choice avoids by construction. Flagged as the far end of a spectrum worth being aware of, not as something to move toward.
8. **A cross-platform, cgo-free SQLite persistence layer** (`modernc.org/sqlite` with a WASM-backed `ncruces/go-sqlite3` fallback for unsupported architectures, plus `goose` migrations) as concrete prior art for durable structured session storage, if liam's session persistence ever needs to move beyond its current mechanism.
9. **Skill catalog injected as XML directly into the system prompt, with retrieval via the existing `view`/read tool rather than a dedicated activation tool** (`skills.ToPromptXML`, `view.go`'s `ViewResourceSkill`) — a third point on the same spectrum as liam's `activate_skill`-tool-with-catalog-in-tool-description and jcode's embedding-based auto-injection; worth weighing if liam's `activate_skill` tool-description token cost ever becomes a real constraint (crush pays a different, always-present token cost by inlining the catalog into the system prompt itself).
10. **Two of three researched Go/Rust coding-agent peers (pi-go, crush) now independently scan `.claude/skills/` (and crush also `.cursor/skills/`)** for skill interop — liam's spec's explicit exclusion of that scan remains a deliberate, now twice-reinforced divergence worth re-confirming rather than revisiting by default.
11. **Two-axis skill visibility frontmatter** (`user-invocable` × `disable-model-invocation`) as a possible addition if liam's Skill frontmatter ever needs to distinguish "force-activatable via slash command but never auto-triggered by the model."
12. **A documented multi-hook-per-event aggregation policy** (parallel execution, dedup by identical command, config-order resolution, deny-beats-allow-beats-silence) — a specific, concrete answer worth weighing against liam's Hooks section, which (like jcode's) doesn't yet specify what happens when multiple hooks on the same event disagree.
13. **Hook-grants-permission wired as a context-scoped, tool-call-ID-keyed pre-approval flag threaded from the hook runner into the permission service** (`permission.WithHookApproval`) — the concrete Go implementation shape for a requirement liam's spec already states but doesn't wire out in detail.
14. **Per-MCP-server `enabled_tools`/`disabled_tools` allow/deny lists**, a finer grain than whole-server enable/disable, worth checking against liam's MCP config scope.
