# Research: pi-go's and jcode's coding-agent harness architecture

Both repos verified as real, active coding-agent CLIs matching what was named — but neither is a close architectural peer of liam. pi-go is a large, "batteries-included" Go harness built on **Google ADK Go**; jcode is a large, performance-obsessed **Rust** harness (not Go at all). Both are useful for contrast rather than for reusable Go patterns.

- `github.com/dimetron/pi-go` — cloned at commit `5de899a7d05862775f40f0ac03cefba2969a127c` in a shallow clone taken 2026-08-31. Go module `github.com/dimetron/pi-go`, `go.mod` requires Go 1.27.0.
- `github.com/1jehuang/jcode` — cloned at commit `fbbde778c868f11e6557fb992eeca014ddd3b853` in a shallow clone taken 2026-08-31. **Not a Go project** — `Cargo.toml` (`github.com/1jehuang/jcode` blob `Cargo.toml:1-6`) declares a Rust 2024-edition workspace of 60+ crates. Included here per the assignment, but its "prior art" value to liam is entirely at the design/feature level, not the Go-implementation level.

## pi-go: what it is

Source: `github.com/dimetron/pi-go` blob `README.md:1-24`.

- "A terminal-based coding agent built on [Google ADK Go](https://adk.dev/). It connects to multiple LLM providers, runs sandboxed tools, integrates LSP, and ships with a process-based subagent system."
- README feature list: multi-provider LLM (Claude, OpenAI, Gemini, Mistral, xAI/Grok, Azure OpenAI, OpenRouter, OpenCode, Ollama), sandboxed tools via `os.Root`, Bubble Tea v2 TUI with Glamour Markdown, JSONL session persistence with branching/compaction/resume, named "model roles," a process-based subagent system, LSP client, AI-generated conventional commits, a Unix-socket JSON-RPC server for IDE integration, a SQLite+embeddings "Memory Palace," Hooks/Skills/MCP extensions, and a skills security auditor (`pi audit`).
- pi-go carries its own primary-source self-comparison against the original TypeScript `pi` coding agent: `docs/DESIGN-COMPARISON.md:1-30` states the two "share a name, a philosophy … and a core loop" but have diverged — TS pi is "a *minimal, radically extensible harness*" (7 tools, 20+ in-process event hooks, no built-in MCP/subagents/web-search) while **Go pi is "a *batteries-included agent runtime*"** that builds in MCP, subagent orchestration with git-worktree isolation, LSP tools, two memory systems, token guardrails, supply-chain skill auditing, OTel tracing, an ACP server/client, ATIF trajectory export, a macOS sandbox wrapper, and a remote-terminal web server, "but has a far thinner in-process extension story (shell hooks + config only, no code-level plugin API)." This self-assessment lines up with what the source shows and is a useful frame: liam sits architecturally much closer to pi-go's own description of the *TypeScript* pi than to pi-go itself.

## pi-go: agent loop / tool interface / provider abstraction

Source: `go.mod:1-46`, `ARCHITECTURE.md:1-60`, `internal/tools/registry.go:1-16,43-56`, `internal/provider/anthropic.go:1-26`.

- pi-go does **not** define its own `Provider` or `Tool` interface. `go.mod` pins `google.golang.org/adk/v2 v2.2.0` (Google's Agent Development Kit for Go), and both abstractions are ADK's: tools are `google.golang.org/adk/v2/tool.Tool` (built via `adk/v2/tool/functiontool`, `registry.go:8-14`), and each provider adapter (`internal/provider/anthropic.go`, `openai.go`, `gemini.go`, `mistral.go`, `xai.go`, `ollama.go`, `openrouter.go`, `opencode.go`, `openai_azure.go`) implements ADK's `model.LLM` (`anthropic.go:24-25`: "`anthropicModel` implements `model.LLM` for the Anthropic API"). This is the same shape kit takes with `charm.land/fantasy` — lean on a third-party agent framework for the loop/tool/provider primitives rather than hand-roll them — but at even larger scope, since ADK also owns session/event-stream plumbing (`internal/agent/eventstream.go`, `internal/agent/retry.go` wrap it).
- `internal/tools/registry.go:43-56` (`CoreTools`) assembles the built-in toolset from per-tool constructor functions into `[]tool.Tool` — read, read_image, write, edit, bash, grep, find, ls, tree, git_overview, git_file_diff, git_hunk, plus session-stats — a flat build-list, similar in spirit to kit's map-of-constructors registration.
- A `ReadLedger`, shared across the read/write/edit tool constructors via `WithReadLedger` (`registry.go:33-39`), enforces a read-before-write check that spans **a whole session**, not just a single tool call — i.e. the harness can refuse to let the model blind-write a file it never read in that conversation. liam's spec has no equivalent cross-tool session-scoped invariant; this is a concrete, narrowly-scoped safety mechanism worth flagging as a candidate for the `write`/`edit` tools.
- **Filesystem sandbox via `os.Root`**: `internal/tools/sandbox.go:41-56` implements a `Sandbox` type whose doc comment is explicit: "Access outside the sandbox is blocked via `os.Root` (Go 1.24+)... Symlinks pointing outside are blocked... Absolute paths are converted to relative." This is a **hard, stdlib-only filesystem jail** applied to every sandboxed tool call, not a permission-prompt convention. liam's spec (issue #41) only escalates out-of-workspace targets to a `prompt` permission decision — it has no structural containment layer preventing a `write`/`edit`/`bash` call from touching `/etc` or `~/.ssh` even under `auto` mode beyond the model choosing not to. `os.Root` is pure Go 1.24+ stdlib (matches liam's "strongly prefer stdlib" philosophy) and is a strong candidate worth surfacing for the read/write/edit tools specifically (bash is harder to sandbox this way, since child processes escape `os.Root`).
- Anthropic auth mimics the official Claude Code CLI: `internal/provider/anthropic.go:19-20` sets `anthropicOAuthBetaHeader` and `anthropicOAuthUserAgent = "claude-cli/2.1.75"` so pi-go can authenticate through Claude's subscription OAuth rather than only a raw API key. (jcode does the same thing more broadly — see below.) liam's spec has no OAuth story; it reads provider/service credentials from env vars only (`OPENROUTER_API_KEY`, `EXA_API_KEY`). Not necessarily a v1 fit, but a real pattern across both repos worth naming as a considered-and-deferred item rather than an unconsidered gap.

## pi-go: config format

Source: `internal/config/config.go:18-100,153-172`.

- Plain **JSON** (not JSONC) — `Config` struct tags are all `json:"..."`, no comment-stripping pass evident (contrast with liam's JSONC decision).
- `Roles map[string]RoleConfig` (`config.go:63`, `RoleConfig` at `config.go:26-32`): named model configurations — README lists `default, smol, slow, plan, commit` — each with its own `Model`/`Provider`/advisor-model overrides, selectable via CLI flag. This is a different answer to "which model runs this turn" than liam's single active `Provider`/`Request.Model` + OpenRouter auto-routing: pi-go lets the *user* statically bind different roles (e.g. a cheap/fast `smol` role for compaction, a stronger `plan` role for planning, a dedicated `commit` role for commit-message generation) rather than delegating model choice to auto-routing per turn. Notably liam's own spec already does something structurally similar in one place — compaction "reus[es] `Provider.Stream` on the session's own current model" rather than a distinct role — so pi-go's named-role mechanism is a direct alternative worth flagging against that specific decision and against the deferred "web_fetch internal summarization model" question (Out of Scope in issue #41).
- `Hooks []HookConfig` (`config.go:18-24`) — a **flat array** with an `Event string` field per entry (plus `Tools []string` filter and `Timeout int`), vs. liam's object-of-arrays-keyed-by-lifecycle-point shape. Functionally similar (multiple hooks, filterable by tool name, per-hook timeout) but a flatter schema — one array to validate instead of four typed sub-arrays.
- `MCP *MCPConfig` (`config.go:153-172`): `MCPServer` supports **both** stdio (`Command`/`Args`) **and** Streamable HTTP (`URL` + `Headers` + `OAuth bool` — "run the OAuth authorization-code flow on first connect"). liam's v1 spec is explicitly stdio-only, with Streamable HTTP and MCP OAuth deferred past v1 — pi-go already ships both, so its `MCPServer` struct is a ready reference for that v2+ ticket when it comes up.
- `MaxDailyTokens int64` (`config.go:87`, `0` = unlimited) backed by `internal/guardrail` (`guardrail.go:13-14`, `DefaultMaxDailyTokens = 50000000`): a persisted, cross-session daily token budget cap, separate from liam's per-session cost/context tracker. liam's spec tracks cost and context per-session only, resetting on `/clear`; pi-go's guardrail persists to disk (`guardrail.go:61-63`, `filePath`) and enforces across the whole day regardless of session boundaries — a different, complementary axis (spend ceiling vs. context-window telemetry) worth naming as a gap liam's spec doesn't currently cover.

## pi-go: skills — security auditing

Source: `internal/cli/audit.go:1-48`, `internal/audit/` (`scanner.go`, `report.go`, `chars.go`).

- `pi audit` is a **dedicated CLI subcommand** ("Scan skill files for hidden Unicode characters") that scans `SKILL.md` files "for hidden Unicode characters that could be used for prompt injection attacks (invisible instructions, BiDi overrides, tag characters)" (`audit.go:32-33`), with `--strip` to remove dangerous characters, `--dry-run`/`--force` for the strip flow, and exit codes `0`=clean, `1`=critical, `2`=warning findings (`audit.go:35`).
- liam's spec addresses skill trust at a coarser grain: "project-level skill loading is trust-gated with a one-time per-project interactive prompt" (issue #41, Skills section) — a yes/no gate on the whole directory, with no content-level scanning of what's actually inside a trusted skill file. pi-go's `audit` package is a concrete, automatable, orthogonal mechanism (static content scanning for a specific attack class — hidden/invisible Unicode, BiDi override characters, tag characters used for steganographic prompt injection) that could complement rather than replace liam's directory-level trust prompt. Worth flagging explicitly as a candidate addition to the Skills trust story, since it's a narrowly-scoped, stdlib-feasible check (Unicode category inspection) rather than a large subsystem.
- Skill discovery locations (`internal/extension/skills.go:435-448`): `~/.pi-go/skills` (user) plus `.pi-go/skills`, `.claude/skills`, **and** `.cursor/skills` (project, walked up from root) — i.e. pi-go actively scans Claude Code's and Cursor's skill directories for interop. liam's spec deliberately excludes `.claude/skills/` from its discovery paths (issue #41: "no scan of `.claude/skills/`") while still wanting "to work with skills I already have installed for Claude Code" (user story 21) via its own `.agents/skills/` convention instead. This is a direct, already-considered divergence — worth noting pi-go took the opposite path (scan the other tool's directories directly) as the alternative liam's spec chose not to take, for whoever revisits that ticket.

## jcode: what it is

Source: `github.com/1jehuang/jcode` blob `README.md:1-20,266-330,624-654`; `Cargo.toml:1-6`.

- Tagline: "The most RAM efficient harness / The most intelligent harness." A Rust TUI coding agent (`Cargo.toml` workspace: root crate `jcode` + 60+ `crates/jcode-*` members) emphasizing runtime resource efficiency (README ships detailed PSS/RAM and startup-latency benchmarks against pi, Codex CLI, OpenCode, Copilot CLI, Cursor Agent, Claude Code, and Antigravity CLI), a semantic-embedding memory system, multi-agent "swarm" collaboration in a shared repo, in-session self-modification ("self-dev mode"), and a first-class browser-automation tool.

## jcode: tool interface

Source: `crates/jcode-tool-core/src/lib.rs:143-166`, `crates/jcode-tool-types/src/lib.rs:60-112`.

```rust
#[async_trait]
pub trait Tool: Send + Sync {
    fn name(&self) -> &str;
    fn description(&self) -> &str;
    fn parameters_schema(&self) -> Value;
    async fn execute(&self, input: Value, ctx: ToolContext) -> Result<ToolOutput>;
    fn to_definition(&self) -> ToolDefinition { /* injects `intent` + escape hatch, below */ }
}
```

- A **hand-rolled** `Tool` trait (`jcode-tool-core`), not built on an external agent framework — closer to zero's approach (per `docs/research/kit-zero-architecture.md`) than to kit's or pi-go's framework-owned tool abstraction.
- **Every** tool schema is centrally injected (`ensure_intent_in_schema`, `jcode-tool-core/src/lib.rs:48-92`) with two properties the model must/may fill in on every call, regardless of what the individual tool declares: a **required** `intent` string ("Required short label shown in the UI: why this call is being made") and an optional `accept_large_output` boolean escape hatch. The latter pairs with a **context guard** that "withholds any tool result too large for the remaining context and states its token cost" (`lib.rs:12-18`) — the model must deliberately re-issue the call accepting the stated token cost to actually receive an oversized result. liam's spec has no analogous "declared reason for this call" convention and no per-call context-cost negotiation; its only large-output handling is the general `web_fetch` truncation-at-~8000-chars and compaction. jcode's `intent`-on-every-call convention is a cheap, generalizable idea (forces the model to state why before every tool call, useful for both the TUI's tool-call rendering and any audit trail) worth flagging against liam's Trace section, which currently records "tool" and "side_effect" but no reason. The context-guard/`accept_large_output` pattern is a more direct alternative to blanket truncation, worth flagging against liam's `web_fetch`/tool-output-size handling generally.
- `jcode-tool-types/src/lib.rs:71-112` (`resolve_tool_name`) normalizes tool-name aliases models emit from other harnesses' training data or provider-side namespacing (`functions.bash` → `bash`, Anthropic OAuth's PascalCase `Read`/`Bash`/`Edit`/`Grep`/`Agent` → jcode's lowercase canonical names, `shell_exec`/`file_read` synonyms, etc.) — a defensive layer against a model calling a tool by a name it learned from a *different* harness. Not something liam's spec currently anticipates; worth a note if liam ever sees models emitting Claude-Code-trained tool names against liam's own differently-named toolset.

## jcode: hooks

Source: `docs/HOOKS.md:1-147` (jcode repo).

- Five lifecycle points, TOML-configured under `[hooks]`: `turn_end`, `session_start`, `session_end`, `pre_tool` (gate), `post_tool`. `turn_end`/`session_start`/`session_end`/`post_tool` are **observers** — "spawned detached, fire-and-forget. They can never block or slow the agent; failures are only logged" (`HOOKS.md:41-45`). Only `pre_tool` is synchronous and blocking.
- `pre_tool` contract (`HOOKS.md:69-83`): the tool's full input JSON on stdin; **exit 0** = allow, **exit 2** = block (hook's stderr, capped at 2000 chars, is returned to the model as the tool error so it can adapt), and **any other outcome fails open** — "other exit codes, timeout (`pre_tool_timeout_ms`, default 5s), missing binary, spawn errors" all allow the call through, with a logged warning. The doc states the rationale explicitly: "Fail-open is deliberate: a broken policy script should degrade to 'no policy' rather than brick every session. If you need fail-closed semantics, make the hook itself robust (it is your trust boundary, not jcode)." liam's spec (issue #41, Hooks section) says "non-zero on a blocking `beforeTool` hook = deny" but doesn't specify the failure-mode question at all — what happens on hook timeout, a missing binary, or a crash. jcode's explicit fail-open default (with the reasoning for it) is directly relevant to that gap and worth surfacing as a concrete precedent, whichever way liam ultimately decides it.
- A recursion guard: every hook process gets `JCODE_HOOKS_DISABLED=1` in its environment so a hook script that itself shells out to the `jcode` CLI doesn't re-trigger hooks recursively (`HOOKS.md:39,146-147`). liam's spec doesn't mention this failure mode; worth a note since liam's hooks also receive `LIAM_*` env vars and a hook script re-invoking `liam` in headless mode is a plausible use case.

## jcode: permissions / shell-command risk (the "reflection gate")

Source: `crates/jcode-command-risk/src/lib.rs:1-33,44-69,146-197`, `crates/jcode-command-risk/src/gate.rs:1-33,74-80`.

This is the single most directly relevant piece of jcode prior art for liam's Permissions section, because it answers almost exactly the question issue #41 explicitly deferred: *"A full classifier-review system … a second model call reviewing every non-trivial action against a rule taxonomy … is a real v2+ candidate, explicitly not built for v1."*

- **Stage 1 — deterministic risk classifier** (`jcode-command-risk`, no model call, no network, "costs nothing on the overwhelmingly common safe path"). Classifies by **blast radius, not command name** — the module doc is explicit that a denylist of `rm -rf` misses `find -delete`, `shred`, `truncate`, `dd`, `>file` (`lib.rs:20-22`). Four levels: `Safe` (run immediately), `Low` (destructive but bounded — inside the working dir, recoverable via git, or under a temp dir — "run, but record it"), `Confirm` (destructive target can't be determined statically), `Catastrophic` (would destroy home/root/credentials — **"Never runs, and no amount of model justification can unlock it"**, `lib.rs:54-57`). The classifier handles wrapper-command unwrapping (`sudo`, `env`, `nice`, `timeout`, `xargs`, `eval`, ...), shell-control-word stripping, opaque `sh -c "..."` recursion into the quoted script, pipe-fed destructive commands (`find ~ | xargs rm`), and redirect-truncation targets — a materially more thorough static analysis than liam's spec's `permissions.commands` prefix-glob matcher (which trusts/denies by literal command-string pattern, not by inspecting what a command's arguments would actually touch).
- **Stage 2 — the "reflection gate," deliberately not a second model call** (`gate.rs:1-19`): "An LLM judge is expensive, adds latency to every borderline call, and can be talked around by the same reasoning that produced the command... Instead the harness refuses once and hands back a structured prompt that forces the *generating* model to do the thinking it skipped." A `Confirm`-level command is refused on first attempt; the *same* model (no separate judge) must retry with a `justification` naming what the user actually asked for, and the retry is checked only for being "substantive" (≥25 chars, not a bare affirmation like "yes"/"ok"/"proceed" — `gate.rs:34-71`) rather than graded for correctness. `Catastrophic` findings are an absolute `Deny` that no justification unlocks (`gate.rs:78-80` onward, `RiskLevel::is_absolute_deny`).
- This is worth flagging strongly against two liam decisions at once: (1) liam's spec's "sole `bash` tool is categorically the highest-risk action a static ruleset can't safely broaden" (so `shell` always prompts even in `auto` mode) — jcode's blast-radius classifier is exactly a "static ruleset" attempt at safely broadening *most* shell calls (the `Safe`/`Low` tiers) while still gating the genuinely ambiguous ones, and its `Catastrophic` absolute-deny tier is a harder guarantee than liam's `prompt`-can-always-be-approved model currently offers for any permission tier. (2) liam's explicitly-deferred "full classifier-review Auto Mode system (second model call per action)" — jcode's authors considered exactly that design and rejected it for cost/talk-around reasons documented in their own source comment, landing on the cheaper self-justification retry instead. Both are candidate ideas for whoever revisits liam's Permissions ticket, not a recommendation to adopt either wholesale.

## jcode: config, MCP, providers

Source: `README.md:329-620` (jcode repo), `docs/HOOKS.md:8-19`.

- Config is TOML (`~/.jcode/config.toml`), not JSON/JSONC — `[provider]`, `[providers.<name>]`, `[hooks]`, `[display]` sections shown in the README's own examples (`README.md:441-487`).
- Provider surface is very wide: native OAuth login flows for Claude, OpenAI/ChatGPT/Codex, Gemini, GitHub Copilot, Azure OpenAI, Alibaba Cloud Coding Plan, Fireworks, MiniMax, Meta Model API, LM Studio, Ollama, plus a generic OpenAI-compatible and Anthropic-compatible profile system (`jcode provider add`) for arbitrary self-hosted endpoints, and 20+ built-in named profiles for aggregators (OpenRouter, OpenCode Zen, DeepSeek, Moonshot, etc.) (`README.md:333-373,614-618`). Every native provider is reachable via **subscription-backed OAuth**, explicitly framed as "use the models you already pay for" (`README.md:329-331`) — the same "impersonate the official CLI's OAuth" pattern seen in pi-go's Anthropic adapter, but jcode does it for nearly every provider it supports, including reading Claude Code's own credential files directly as a fallback source during setup (`README.md:805-816`).
- MCP config (`README.md:540-564`): jcode reads Claude Code's own `~/.claude.json`/`.mcp.json`/`.claude/mcp.json` **live, on every load**, "so migration...take[s] effect without leaving a stale snapshot" — i.e., no one-time import/copy, actual live delegation to another tool's config files as a first-class config source, alongside jcode's own `~/.jcode/mcp.json`/`.jcode/mcp.json`. jcode's MCP is stdio-only in the current version ("HTTP/SSE entries...are recognized and skipped with a log line," `README.md:564`) — same v1 scope as liam's spec. An older planning doc, `docs/plans/MCP_SKILLS_PLAN.md` (stale — its file paths like `src/mcp/mod.rs`, `src/skill.rs` don't match the current 60-crate layout, so treat as historical intent rather than current state), describes agent-driven **dynamic MCP server registration** at runtime (`mcp_connect`/`mcp_list`/`mcp_disconnect` tools letting the model itself add an MCP server mid-session) — a materially different model than liam's static, user-edited `mcpServers` config section; flagged as a candidate idea (self-service MCP) rather than confirmed current jcode behavior, since the plan doc predates the crate split and its implementation status wasn't independently verified in this pass.

## jcode: skills — semantic/embedding-driven activation

Source: `README.md:268-290,652`.

- jcode's skill activation is **not** primarily catalog-in-a-tool-description like liam's decided `activate_skill(name)` mechanism. Per the README: "Skills are not all loaded on startup. The conversation is embedded as a semantic vector, and will automatically inject a skill if there is an embedding hit similar to memories. The agent has a skill tool for you to manually activate a skill at anytime. You may also activate via slash commands." This is the same embedding/vector-similarity mechanism jcode uses for its broader "Memory" system (README:268-276: turn embeddings queried by cosine similarity, with an optional "memory sideagent" that verifies relevance before injecting into context) applied to skill selection specifically. liam's spec deliberately keeps the skill catalog "embedded in [the `activate_skill`] tool's own description rather than the system prompt, to keep the base prompt minimal" — a static, enumerable, hallucination-resistant (name-enum-constrained) approach. jcode's embedding-based auto-injection is a genuinely different mechanism (no context cost for an unused catalog, but requires an embedding model at runtime — jcode ships local ONNX/MiniLM inference behind a Cargo feature flag for exactly this) worth flagging as an alternative liam could weigh if the skill-catalog token cost ever becomes a real constraint, at the cost of the local-embedding-model dependency liam's stdlib-first philosophy would need to accept as a deliberate exception (same category of tradeoff already made once for the fff-backed `find`/`grep` tools' external-binary fallback).

## jcode: features with no liam analogue at all

Source: `README.md:311-326,624-631`.

Flagged for completeness, not as design input — these are large subsystems outside anything liam's spec scopes toward, but worth naming since the assignment asked for anything "interesting or different":

## Summary: candidate ideas worth surfacing (not recommendations)

Per the task's framing, these are flagged as things worth someone's attention against liam's already-decided spec, not adoption decisions:

1. **`os.Root` filesystem sandboxing for read/write/edit** (pi-go, `internal/tools/sandbox.go`) — a stdlib-only hard containment layer, complementary to liam's permission-prompt model, that liam's spec doesn't currently have at all.
2. **Session-scoped read-before-write ledger** (pi-go, `ReadLedger`) — cheap, narrowly-scoped safety invariant for `write`/`edit`.
3. **Skill-file content security scanning** (pi-go, `pi audit` — hidden Unicode/BiDi/tag-character prompt-injection detection) as a complement to liam's directory-level trust-gate prompt.
4. **Named model roles** (pi-go, `config.Roles`) as an alternative/complement to relying solely on OpenRouter auto-routing + a single reused-model compaction call, for cases like a distinct cheap compaction model or a distinct planning model.
5. **A deterministic blast-radius shell-command risk classifier plus a "reflection gate"** (jcode, `jcode-command-risk`) as concrete prior art directly against liam's deferred "full classifier-review Auto Mode" ticket — notably, an alternative that explicitly avoids a second model call.
6. **Explicit fail-open semantics and documented rationale for hook failure modes** (jcode `pre_tool` hooks) — liam's spec doesn't currently specify what happens on a hook timeout/crash/missing binary.
7. **A required `intent` field injected into every tool call schema, plus a context-cost-aware "accept this oversized result" escape hatch** (jcode `jcode-tool-core`) — relevant to liam's Trace (no "why" is currently recorded) and to `web_fetch`/tool-output-size handling generally (currently blanket truncation only).
8. **Per-account/per-provider subscription OAuth** (both repos, especially jcode's breadth and pi-go's Claude-Code-mimicking headers) as a considered-and-named gap against liam's env-var-only credential model.
9. **MCP config read live from another tool's config files** (jcode reading Claude Code's `~/.claude.json`/`.mcp.json` on every load) vs. liam's own-file-only MCP config — a different interop strategy than liam's Skills-directory precedent of "don't scan the other tool's directory, use your own."
10. **Embedding-driven automatic skill activation** (jcode) as a genuinely different alternative to liam's static enum-constrained `activate_skill` catalog, at the cost of a local-embedding-model dependency.
