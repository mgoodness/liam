# liam keeps its hand-rolled Tool/Provider interfaces over charm.land/fantasy

liam is 2-for-2 an outlier among surveyed Go coding-agent harnesses in hand-rolling its `Tool` (`internal/tool/tool.go`) and `Provider` (`internal/provider/provider.go`) abstractions rather than delegating to an external agent framework — pi-go builds on Google ADK Go, crush (Charm's own CLI, on the same Bubbletea/Lipgloss stack liam's TUI uses) builds on `charm.land/fantasy` ([docs/research/crush-prior-art.md](../research/crush-prior-art.md), [docs/research/pi-go-jcode-prior-art.md](../research/pi-go-jcode-prior-art.md); [issue #160](https://github.com/mgoodness/liam/issues/160)). This ADR records keeping the hand-rolled interfaces as a considered position, not an oversight.

Direct inspection of `fantasy` v0.41.3 found the costs outweigh the benefit for liam's current shape: its `go.mod` requires the OpenAI SDK, Anthropic SDK, AWS SDK v2, and GCP auth/genai/cloud/storage/monitoring plus a full OTel stack as direct, non-optional dependencies (~60+ transitive modules) with no independently-importable subset — "provider adapters only" costs the same footprint as full adoption. Its `AgentTool` interface has no analogue to liam's `Safety`/`SideEffect` (kept for Trace's audit categorization, ADR-0004), so adopting it would still require a wrapper/registry maintained outside `fantasy` for exactly that part. Its `Provider.LanguageModel` streaming shape differs from liam's `iter.Seq2[Event, error]` sum type (`TextDeltaEvent`/`ToolCallEvent`/`ToolResultEvent`/`DoneEvent`), so adopting the provider layer alone would still require a hand-written adapter between the two shapes — relocating hand-rolled code rather than eliminating it. And `fantasy`'s own provider story targets first-party vendor SDKs (OpenAI/Anthropic/Bedrock/Vertex), not the OAuth-based, aggregator-adjacent provider (GitHub Copilot, issue #100) liam is actually about to add — it doesn't close that gap.

This tracks `CODING_STANDARDS.md`'s stdlib-first stance (third-party dependencies as narrow, deliberate exceptions) and `CONTEXT.md`'s "minimal coding-agent harness" self-description: a single-provider (OpenRouter), single-HTTP-client harness has no non-trivial, already-solved problem `fantasy` solves for it today.

## Considered Options

Partial adoption — `fantasy`'s provider adapters only, keeping liam's own `Tool` interface and Safety model. Rejected: `fantasy`'s dependency graph doesn't shrink based on which providers are actually used (all major vendor SDKs are direct top-level requires), so this costs the same dependency footprint as full adoption while still requiring a hand-written adapter between `fantasy`'s `LanguageModel` streaming shape and liam's `Event` sum type.

Full adoption. Rejected: no analogue to `Safety`/`SideEffect` in `AgentTool`, meaning liam keeps a hand-maintained wrapper outside `fantasy` for exactly the part of `Tool` that exists for Trace's audit design — losing control of the `Tool`/`Provider` shape without reducing hand-maintained code. `fantasy`'s own provider surface (first-party vendor SDKs) doesn't match liam's trajectory (OpenRouter-first, aggregator-adjacent OAuth providers per #100) either.

## Consequences

liam continues to hand-write and hand-maintain its own provider adapters (currently OpenRouter; #100's GitHub Copilot provider next) and its own `Tool`/agent-loop plumbing, with no shared framework absorbing that maintenance. If liam's provider count grows large enough that this becomes the dominant engineering cost, revisit — but re-inspect `fantasy`'s per-provider independence and dependency graph at that time rather than assuming this finding still holds on whatever version exists then.
